## 0. 前提と範囲

### 0.1 ゲート

- 02 §4 #17のUI部分: 提案に対して両ユーザーが画面から回答できる(yes=[参加する] / defer=[今回は見送る]のUI 2択)。回答の記録と状態遷移を確認する。noはAPI専用で画面に置かない(noのAPI部分はF4aで証明済み)
- バックエンド(`/v1/latches`の一覧・取得・回答・取り消し・離脱・見送り理由)はF4a・F4bで完成済み。F4cは画面と、§2の小さなAPI追加のみを行う

### 0.2 オーナー合意(2026-10-20)

| # | 論点 | 合意 |
|---|---|---|
| 1 | 画面の範囲 | 提案〜成立一式(Homeの到着カード・提案(1対1/グループ)・回答待ち・見送った+理由シート・成立しなかった・つながった)。§0.3は作らない |
| 2 | どの意思への提案かの表示(prototype README §7 #4) | LatchDTOへ自分側のIntent ID(`my_intent_id`)を追加し、Homeの該当する意思カードを「回答を待っています」にする(試作品どおり) |
| 3 | 見送り後の説明の「一度だけ」(01 §10) | 端末の中(localStorage)に、つながり/機会の別で記録する。実際に動作させてから見直す(§1.5・§4) |

## 1. 画面

### 1.1 URL

| URL | 用途 |
|---|---|
| `/latches/:id` | 提案1件の画面。開くたびに`GET /v1/latches/{id}`で状態を取得し、§1.2の表で表示を切り替える |
| `/latches/:id/shelved` | 見送った直後の画面(押した本人だけが使う) |

どちらも登録済みユーザーのみ(既存のRequireAuthで保護)。

### 1.2 `/latches/:id`の表示の切り替え

| サーバーの状態 | 表示(ボード) |
|---|---|
| `proposed`・`partial_accept`で`my_response`がnull | 提案(Proposal / ProposalGroup) |
| `proposed`・`partial_accept`で`my_response`がyes | 回答待ち(Awaiting) |
| `matched` | つながりました(Matched) |
| `my_response`がdefer | 見送った画面(`/latches/:id/shelved`)へ置き換え遷移する |
| `rejected`・`expired`・`cancelled`(成立を経ていない) | 成立しませんでした(NotEstablished) |
| `cancelled`(成立を経た=`proposal`キーがある) | NotEstablishedの形で「このつながりは終了しました」(README §6の文言・終了の理由は区別しない) |
| 404 | 「この提案は見つかりませんでした」とHomeへ戻るボタン(ボードに無いため実装の裁量・NotEstablishedの形を使う) |

判定は上の行から順に行う(deferの判定は状態より先に置く)。API経由でnoと回答した本人は、閉じた状態の行(成立しませんでした)に当たる(noは画面に置かないため専用の表示を持たない)。

### 1.3 各画面

- **提案**: 夜の配色の「部屋」(`theme: dark`・`room proposal`)。1対1は灯りの半円(`is-arrived`)、3人以上はグループの円(groupDisc)と「あなたを含むN人で成立します」(Nは`participants_count`)。見出し「条件が合う候補があります。」・回答期限(`response_deadline`のJST表示と残り時間・残り時間は15秒ごとに更新)。ボタンは[参加する](主)・[今回は見送る](副)の2つだけと、注記「お互い(グループは全員)が参加すると、はじめて相手が見えます。」。左上は「あとで回答する」でHomeへ
- **回答待ち**: 半円は押し込まれた形(`is-pressed`)。見出し「相手の回答を待っています。」と回答期限。[回答を取り消す](控えめなボタン)。それ以上の説明・催促は出さない(01 §10)
- **つながりました**: 1対1は相手の表示名・アイコン・自己紹介と「M月D日 HH:MM につながりました」、グループは全員の名前とアイコン。「重なったところ」は`proposal`から作る(つながり=主題・預け方・人数・地域、機会=主題・日時・場所・人数・予算。README §7 #5。値が無い項目は「指定なし」)。下のボタンは「あとで」(Homeへ)のみ
- **成立しませんでした**: 棚の半円と「この提案は成立しませんでした。」「あなたの意思は、そのまま預けています。」・[預けている一覧へ]
- **見送った**(`/latches/:id/shelved`): 縦書き「そっと、棚に戻しました。」・「今回の提案は見送りました。あなたの意思は、そのまま預けています。」・説明(つながり=「この相手との提案は今後届きません。」/機会=「条件が変われば、また届くことがあります。」・§1.5)・[閉じる](Homeへ)・控えめな「見送った理由を残す(任意)」。理由はシートで4択(いまは余裕がない=`no_capacity`/日時や場所が合わない=`schedule_mismatch`/なんとなく、今回は=`just_not_now`/その他=`other`)から選び[残す]で`POST /v1/latches/{id}/defer-reason`、または[スキップ]。送信後はトースト「ありがとうございます。相手には伝わりません。」。formは`GET /v1/latches/{id}`の`form`から取る

アイコンは`has_icon`がtrueのとき既存の`GET /v1/users/{user_id}/icon`を画像として読み、falseのときは試作品の無地のアバターを出す。

### 1.4 操作と状態の切り替え

- [参加する]: `POST /response {response:"yes"}`。半円を押し込む動き(約0.52秒)のあと、応答が`matched`ならその場でつながりました(演出あり)、それ以外は回答待ち
- [今回は見送る]: `POST /response {response:"defer"}`。棚に戻す動き(0.76秒)のあと`/latches/:id/shelved`へ置き換え遷移
- [回答を取り消す]: `POST /response/retract`。提案の表示へ戻る
- 送信中はボタンを押せなくする(二重送信の防止)
- 失敗(400・404・通信失敗): `GET /v1/latches/{id}`を取り直して§1.2の表で正しい表示にし、短い一文(「この提案には、もう回答できません。」等)を出す
- 回答待ちの表示中は30秒ごと、および画面に戻ったとき(window focus)に取り直し、`matched`・不成立へ変わったら表示を切り替える
- 成立の演出(かちっ→にじむ・Matched の`is-fresh`)は、その場で成立を見届けたとき(自分の[参加する]の応答が`matched`、または回答待ちの表示から`matched`へ切り替わった)だけ出す。URLを開き直したときは噛み合った状態(`is-latched`)を静止で出す
- 動きは`prefers-reduced-motion`で瞬時の切り替えになる(latch.cssの既存の規定)

### 1.5 見送り後の説明の「一度だけ」

- localStorageのキー`latch.deferNoteSeen.connection`・`latch.deferNoteSeen.occasion`に記録する。見送った画面を表示した時点で、そのformの説明を出してから記録する
- 記録はformの2種類だけで、Intentの件数とは関係ない。データを消去した端末・別の端末では、formごとに最初の見送りでもう一度だけ出る(最大2回)
- localStorageが使えない環境では毎回出す(見逃しを避ける側に倒す)
- 読み書きは`src/latches/deferNote.ts`の1か所に閉じ、サーバー保存へ変える場合はここを差し替える。オーナーが実際に動作させたうえで見直す(§4)

### 1.6 Homeの変更

- `GET /v1/latches?type=proposals`を意思の一覧と並行して取得し、一覧の上に提案ごとの到着カード(`arrival`)を出す。文言は未回答=「提案が届いています」/yes済み=「相手の回答を待っています」(`is-pressed`)、下に「回答期限 … まで」と3人以上なら「· N人」。押すと`/latches/:id`
- 進行中の提案の`my_intent_id`と一致する意思カードは、状態表示を灯りの「回答を待っています」にする(01 §10の表示語・試作品と同じ)
- 未回答の提案があるときだけ右上の器(`vessel`)に灯り(`is-lit`)を入れる(現在の常時点灯を改める)
- 提案の取得だけが失敗した場合は到着カードを出さずに意思の一覧を表示する(提案が取れないことで預けた意思まで見えなくなるのを避ける)

## 5. 試験

### 5.1 単体・統合(毎コミット)

- worker: `my_intent_id`が自分側のIntent IDであること(1対1・グループ)、成立前のLatchDTOに相手の情報が増えていないこと(#20の既存試験へ追加)
- web(画面試験・APIの応答を差し替える既存方式):
  - §1.2の表の全行で正しい表示になること
  - 提案画面のボタンが[参加する]・[今回は見送る]の2つだけで、noの操作が無いこと
  - 各操作で正しいリクエストが送られること・送信中は押せないこと・失敗時に取り直して正しい表示へ戻ること
  - 回答待ちの30秒ごとの取得と表示の切り替え(偽の時計で早送りする)
  - 成立の演出が、その場で見届けたときだけ出ること
  - 見送りの説明がformごとに初回だけ出ること・localStorageが使えないときは毎回出ること
  - Homeの到着カード・意思カードの「回答を待っています」・器の灯り・提案の取得失敗時にも意思の一覧が出ること

### 5.2 ゲートE2E(#17のUI 2択)

`apps/web/e2e/`に、2つのブラウザ(Playwrightのbrowser context)で2人のユーザーを演じる試験を追加する。

1. 2人が画面から登録し、同じ文章の意思を預ける。裏側の処理が提案を作るまで待つ(開発専用の観測API`GET /v1/dev/latches`で出現を待つ)
2. 成立の筋: AがHomeの到着カードから提案を開き[参加する]→回答待ち。Bが[参加する]→Bは「つながりました」。Aの回答待ちは画面に戻ったときの取得で「つながりました」に切り替わる
3. 見送りの筋(別の2人): Aが[今回は見送る]→見送った画面と説明が出て、理由を残せる。Bの画面は「成立しませんでした」になる
4. 回答の記録と状態の変化(matched・不成立)を観測APIでも確かめる
5. 提案画面にnoの操作が無いことを確かめる

30秒ごとの定期取得はE2Eでは待たず(試験時間を延ばさないため)、§5.1の単体試験で証明する。
