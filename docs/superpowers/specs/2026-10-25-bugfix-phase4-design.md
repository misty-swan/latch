### 0.4 原因の調べ(2026-10-25・読み取りのみ)

- #47: 反映確認(vector_reflection)が「反映済み」とするのは、キューの実行のgetByIdsで自分のベクトルが見えたとき。後から保存した側Bのその場の評価(応答の後の処理)の照会で相手Aが見えることは保証しない。記録では、同じ20秒に作成された速い4件は同じ経路で相手を見つけており、経路ではなく照会ごとに古い状態と新しい状態が混ざる(キューの照会は約10ms・その場の照会は約165msで、別の場所で処理されていると推定)。相手を見落としたBは`last_evaluated_at`が書かれて30分の抑制に入り(evaluate.ts)、Aの評価し直しはBの保存より前に終わり、毎分Cronも拾わない((h)はつながりIntentだけ・bucketとcatch-upは抑制を守る・(g)は未評価だけ)。このためB自身の反映確認(約180秒後)まで救われない。Cloudflareの文書は「upsertは非同期で、照会できるまで通常数秒」とだけ書き、場所ごとの一貫性には触れていない
- #32: Accessの検証は原因ではない(451件中0.1秒以上は1件)。応答の前はD1の往復2回(Active Intentの件数の確認と挿入)とKVの往復1回。遅い保存は(a)の開始から170〜210秒の約40秒(反映確認の後の評価し直しが76件重なる時間帯)に集中し、その外ではp95 0.1〜0.25秒
- #43: 失敗するのはmatch_candidatesへのupsert(intents.idへの外部キーの違反と推定)。評価がLayer 1で相手の行を読んだ後に削除のD1 batchが確定し、その後のupsertが失敗する。間に挟まる孤立したベクトルの削除(約1秒)が窓を広げる(24件中24件)。評価全体が止まり他の候補の提案も落ちる。Cronの遅延再評価は次の回でやり直されるが、反映確認の評価はやり直されない
- #44: 40041の意味は公開文書に無い(書き込みの一時的な拒否と推定・未確認)。(c)の準備でだけ出るのは、直前の(d)の後始末でベクトルを消した直後に孤立したベクトルの削除とupsertが重なるためと見られる。キューの60秒後のやり直しで回復している。孤立したベクトルの削除の失敗がINTERNALになるのは、例外の分類(errors.ts)がVectorizeの削除の例外を分類しないため
- #45: 保留の解放は、参加者の保留(最大500件)を1件ずつ直列に3〜5往復で処理する。上限に届いた後も1件あたり3往復を読み続ける
- #42: 書き込みは`apps/worker/src/llm/external-send.ts`にあり、精度ゲートの指紋の対象ではない(対象は呼び出し側の`llm/mode.ts`)。external-send.tsの中だけで直せば`pnpm eval:gate`の採り直しは要らない。ログのerror_codeは常に固定の"D1_ERROR"
- #46: §9のk6の要約で接続の保持時間の最小が106秒(本来約300秒)。途中で閉じた接続の不足時間の合計(約490秒)が送信の不足(95件×5秒)とほぼ一致する。途中で閉じた接続は、どの指標にも数えられない(`tools/load`の(c)シナリオ)
- #37: 頼っているのは`apps/web/e2e/flow.spec.ts`の2・3。6と`pwa-flow.spec.ts`は頼っていない(pwa-flowはbeforeEachで残りの意思を消している)

## 1. #47 直近のベクトルをD1にも控えて補う(オーナー決定2・3)

### 1.1 問題

Layer 2 Candidate RetrievalはVectorizeの照会だけに頼る。Vectorizeは照会によって数十秒〜数分古い状態を返すことがあり、相手の反映確認が済んだ後でも相手が見えないことがある(§0.4)。見落とした意思は30分の抑制に入り、自分の反映確認の後の評価し直しまで提案されない。

### 1.2 表

新しい表`recent_vectors`(マイグレーション0009と戻す手順):

| 列 | 型 | 内容 |
|---|---|---|
| intent_id | TEXT 主キー | intents.idへの外部キー(ON DELETE CASCADE) |
| embedded_at | INTEGER | 埋め込みの時刻(intents.embedded_atと同じ値) |
| vector | BLOB | 埋め込みのベクトル(float32の並び。bge-m3は1,024次元で約4KB) |

- 索引: `embedded_at`
- 1件約4KB。(a)の500件で約2MB
- formとstatusは持たない(評価の照会でintentsと結合して絞る)

### 1.3 書き込みと削除

- 書き込み: 新しい埋め込みを計算してVectorStoreへupsertする箇所(第1段・バックフィルなど、埋め込みを計算するすべての経路)で、同じ時刻にrecent_vectorsへupsertする(同じintent_idは上書き)。書き込みの失敗は第1段の失敗として扱わない(ログに残して進む。補いが無いだけで従来の動作に戻る)
- 削除: 意思の削除は外部キーのCASCADEで消える(削除のD1 batchに明示の削除を加えるかは実装の裁量)。埋め込みから15分(RECENT_VECTOR_TTL_MS)を過ぎた行は毎分Cronの保持期間の処理で消す
- 15分は、反映確認の打ち切り(8分)より長い余裕として選んだ

### 1.4 評価での補い

`evaluate.ts`のVectorStoreの照会(filter={form, status:"active"}・topK=100)の直後に:

1. D1から、`recent_vectors`と`intents`を結合し、intents.form=起点のform・intents.status='active'・embedded_at≥now−15分・自分以外の行を、embedded_atの新しい順に最大50件(RECENT_VECTOR_SUPPLEMENT_MAX)読む。照会の結果に既にあるidは除く(SQLで除くか読んだ後に除くかは実装の裁量)
2. 読んだベクトルと起点のベクトルのコサイン類似度を計算し、照会の結果と合わせて類似度の降順に並べ、topK(100件)で切る
3. 以降(自分の除外・Layer 1・孤立したベクトルの自己修復・Layer 3〜)は従来どおり
   - 補った行はD1に意思の行があるので、孤立したベクトルの自己修復の対象にならない
   - 類似度は照会と同じコサイン類似度で、Vectorizeの値と同じ尺度であること(浮動小数の誤差の範囲)を単体試験で確かめる
4. ベクトルの次元がずれる行(モデルの変更の後に残った行など)は読み飛ばす

ローカル(インメモリのVectorStore)でも同じ処理を通す。インメモリは常に最新を返すため補いは重複として除かれ、結果は変わらない。

### 1.5 記録

`pipeline.stage2.timing`(または評価の完了の記録)と`match_events.payload`に、照会が返した件数(retrieval_count)と補った件数(supplement_count)を載せる。許可リスト方式のログへ項目を足す。負荷試験で、補いが提案につながった件数を確かめられるようにする。

### 1.6 試験

- 単体: コサイン類似度の計算・並べ替えと切り詰め・重複の除外・次元のずれの読み飛ばし
- 統合: VectorStoreの照会が相手を返さない状態(照会だけを古い状態に固定する試験用のVectorStore)で、recent_vectorsにある相手がLayer 1以降へ進み提案される。15分を過ぎた行・paused・別formの行は補わない。削除した意思の行が消える。Cronの保持期間の処理が15分を過ぎた行を消す

## 2. #32 Intent保存

### 2.1 設計

- Active Intent上限(5件)の確認(SELECT count)と挿入を、条件付きの1文(INSERT … SELECT … WHERE (SELECT count(*) …) < 5 など)にまとめ、応答の前のD1の往復を1回減らす。上限を超えたときの応答(409 ACTIVE_INTENT_LIMIT等の現在の応答)と、draftの保存(上限を数えない経路があれば)の振る舞いは変えない
- `intents.create.timing`に、まだ計測の無い段(認証のKVの読み・上限の確認)を分けて載せる
- 負荷試験で目標に届かなければ、反映確認の後の評価し直しの重なりを軽くする手を検討する。ただし主キューの同時実行数の上限は第3回でオーナーが採らなかった方法なので、必要ならオーナーへ相談する

### 2.2 試験

- 統合: 上限ちょうど(5件目は成功・6件目は従来と同じ応答)・同時に2件保存して上限を超えない
- 既存のIntent APIの試験がすべて通る

## 3. #43 削除と評価の競り合い

### 3.1 設計

- 評価の中の孤立したベクトルの削除を、match_candidatesへのupsertの後へ移す(窓を約1秒縮める)
- match_candidatesへのupsertが外部キーの違反で失敗したときは、その時点でD1に行の無い相手(削除された相手)を候補から除いて1回だけやり直す。やり直しも失敗したら従来どおり失敗として記録する
- 外部キーの違反の判定はD1の例外の本文で行い、errors.tsの分類名(D1_CONSTRAINT)と矛盾しないようにする

### 3.2 試験

- 統合: Layer 1の後・upsertの前に相手を削除する状況(試験用の差し込み口かD1の直接操作)で、評価が残りの候補で完了し、他の候補の提案が作られる

## 4. #44 第1段のupsertと孤立したベクトルの削除

### 4.1 設計

- 応答の後の第1段のVectorStoreのupsertに、1秒・2秒の短いやり直し(最大2回)を足す。やり直しても失敗したら従来どおりキューのやり直し(10秒・30秒・60秒)へ回す。応答の後の処理の30秒の上限に収まることを確かめる
- errors.tsの分類を広げ、Vectorizeの削除(deleteByIds)の例外にも分類名(VECTOR_DELETE_*)を付ける

### 4.2 試験

- 単体: 分類名
- 統合: upsertが1回失敗して2回目に成功すると第1段が成功する・3回失敗するとキューのやり直しへ回る

## 5. #45 削除の後の保留の解放

### 5.1 設計

- 保留の解放を「対象の保留をまとめて読む → メモリで解放・提案の可否を決める → まとめて書く(db.batch)」の3段にする。1件ずつの直列の往復をやめる
- 通知上限に届いた参加者の保留は、読んだ後の判断で書き込みを省く(往復を増やさない)
- 時間の予算(例: 20秒)を設け、超えた分は毎分Cronの保留の解放(release_held)に任せる
- 解放の結果(どの保留が解放され、どの提案が作られるか)は従来と同じであること

### 5.2 試験

- 統合: 既存の#27の試験と保留の解放の試験がすべて通る。保留が多い(例: 100件)意思の削除で、往復の回数が件数に比例しない(D1の呼び出しの回数を数える)。予算を超えた分がCronで解放される

## 6. #42 外部送信の集計の書き込み
