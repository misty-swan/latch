## 1. エラーの分類と段ごとの記録

### 1.1 問題

`pipeline/errors.ts` の `errorCodeOf` は、例外の文の最初の「:」より前が `^[A-Z0-9_]+$` のときだけ符号として使い、それ以外は既定値(第1段は `EMBEDDING_FAILED`、他は `INTERNAL`)にする。Vectorizeの例外(`VECTOR_GET_ERROR (code = 40007): …`)・drizzleが包んだD1の失敗(`Failed query: …`)・キューの送信の失敗は、どれも既定値になる。削除API(`routes/intents.ts`)は `catch {}` で例外を捨て `INTERNAL` 固定で記録する。このため#16・#17・#20の原因をログから切り分けられない。

### 1.2 設計

- `errorCodeOf` を、例外の `cause` を辿り、次の安全な分類名へ写す形にする。個人情報や文の中身はログに出さない(許可リストの `error_code` に分類名だけを入れる)
  - Vectorize: `VECTOR_<操作>_<code>`(例: `VECTOR_GET_40007`・`VECTOR_UPSERT_<code>`)
  - D1: `D1_OVERLOADED`・`D1_ERROR`(drizzleの包みの内側の文で判定)
  - キュー: `QUEUE_SEND_FAILED`
  - Workers AI: `AI_<数字>`(文の先頭の数字の符号)
  - その他: 例外の型名(`TypeError` 等)。判定できないときは従来の既定値
- 第1段に `layer` を付けて段を出す: `embed`・`upsert`・`d1`・`emit`(許可リストの既存項目 `layer` を使う)
- 削除APIの各段の所要時間を出す: 事件名 `intents.delete.timing`、`layer=vector|d1_children|d1_intent`・`latency`。ベクトル削除の失敗の `error_code` は1.2の分類にする
- ベクトルを書く経路を区別する: `pipeline.stage1.completed` に `layer=queue|backfill|repair` を付ける
- ログの許可リストの項目は増やさない(既存の `error_code`・`layer`・`latency` の範囲で行う)

## 2. 毎分Cronが止まらないようにする(#15)

- `getByIds` は、VectorStoreのVectorize実装(`vectorstore/vectorize.ts`)の中で20件ずつに分けて呼ぶ。呼び出し側(修復・群評価・反映確認)は上限を意識しない。`deleteByIds` の上限は公式の文書で確かめ、上限があれば同じく実装の中で分ける
- `runScheduledPipeline` の前半7走査も、既存の後半と同じく `runIsolated` で隔離する。1つの走査が失敗しても後ろの走査は動く(06 §2の「既存7走査は失敗を伝播させる」の記述を改める)
- インメモリのVectorStoreに、本物と同じ件数の上限(getByIds 20件)で例外を出す試験用の設定を足し、修復・群評価・反映確認・予算アラートの試験で使う
- 修復の点検の対象の取り出し(並び順も続きの位置も無い `LIMIT 500`)は今回は変えない。500件を超えるのは公開の後なので、06 §2に既知の制約として書く

## 3. 反映確認・修復・待ち時間

### 3.1 打ち切りと修復の除外(#21)

- `PIPELINE.REFLECTION_GIVE_UP_MS` を5分から8分にする。最後の確認は8分30秒より前に終わり、`PENDING_STALE_MS`(10分)の残留の掃査とはぶつからない。この関係を単体試験で固定する
- 修復の除外を打ち切りから切り離す。修復は、次のどちらかに当たる意思を点検しない
  - その意思の現在のversionの `vector_reflection` の行が `pending` である
  - `embedded_at` から `PIPELINE.REPAIR_GRACE_MS`(新設・10分)以内である

### 3.2 反映確認の途中の例外(#23)

- 反映確認の `getByIds` の例外は「未反映」と同じに扱い、次の遅延で送り直す(打ち切りの判定は従来どおり行の作成からの経過で行う)
- 送り直し(キューへの送信)の例外は、受け取ったメッセージの `retry({ delaySeconds })` でやり直す。`max_retries: 3` を超えたものは既存のDLQで `dead` になる
- 反映確認の失敗のログは事件名を `pipeline.reflection.failed` に分け、`intent_id` を付ける

### 3.3 Cronのバックフィルの直後の評価(#22)

- `runEmbeddingStage` は計算したベクトルを返す。バックフィルはそれを `evaluateIntent(..., { vector })` に渡す
- 評価がnullを返したときは `backfilled` に数えない
- #9の試験(Cronのバックフィルで作った提案をその場で送る)は、反映の遅れるVectorStoreで書き直す

### 3.4 計測(#24)

- `EvaluateOptions` に評価の起点(`origin`: `embedding_completed`・`vector_reflection`・`cron_backfill`・`cron_delayed`・`cron_other`)を足し、`stage2`・`stage2_group` のデータ点のblobに入れる(06 §7のデータ点の並びを更新)
- 2件のデータ点を結び付ける鍵として、評価ごとに作る乱数(どこにも保存しない)を両方のblobに入れる。イベントのidや意思のidは入れない(08 §6の方針)
- `writeDataPoint` を `try/catch` で包み、失敗は `warn`(`pipeline.metrics.failed`)だけにする。計測の失敗で評価をfailedにしない

### 3.5 通知とキューの待ち(#19・#18)

- 主キューの消費で、1件のメッセージの処理が通知を作ったら、その場で `ctx.waitUntil(flushPush(...))` を呼ぶ(対象はそのメッセージの処理で作った通知に限る。二重送信は既存の行ごとの順番取りで防ぐ)。バッチの最後の送出は取りこぼしの回収として残す
- 主キューの消費の `max_batch_timeout` を1秒にする(既定とstagingの両方。設定できる範囲は公式の文書で確かめる)。`max_batch_size` は変えない

## 4. 第1段の失敗(#17)

- 第1段を段ごとに扱う
  - `embed`・`upsert`・`d1`(`embedded_at` の更新)の失敗: 起点の行は `pending` のまま、受け取ったメッセージの `retry({ delaySeconds })` でやり直す(遅延は10秒・30秒・60秒の順)。`max_retries` を超えたものは既存のDLQで `dead` になり、従来どおり5分後のCronのバックフィル(e)が拾う
  - `emit`(`embedding_completed` と `vector_reflection` の投入)だけの失敗: ベクトルと `embedded_at` は書けているので、投入だけをやり直す(同じく `retry`)。投入できないまま終わった場合の救済は、従来どおり未評価の回収(g)
- 06 §5の「Embedding失敗は再試行なし・Cronのバックフィルが回収」を、上の形に改める
- 最終の確定は、§1の分類を入れたstagingで原因(D1の混雑・Vectorizeの受け付けの拒否・Workers AIの上限・キューの送信)を確かめた後に行う。原因が想定と違えば、新しいissueに登録し、オーナーに報告する

## 5. 削除(#16・#20)

### 5.1 削除の遅さ(#16)

- `match_events(source_intent_id)` と `match_events(status, created_at)` の索引を足す(マイグレーション。戻す手順も書く)
- `group_candidates` の削除は、表全体の `json_each` をやめ、本人の意思を含む候補に絞ってから消す
- 削除APIのD1の削除を `db.batch` にまとめる
- 後始末のスクリプト(`tools/load/cleanup.mjs`)に `fetch` の時間切れと再試行を入れる
- 効果はstagingでしか測れない(§9)

### 5.2 削除の後のベクトルの書き戻し(#20)

- ベクトルを書く4経路(Cronのバックフィル・Cronの修復・状態の同期 `syncVectorStatus`・第1段のEmbeddingの後)は、upsertの直前に意思の行の存在とstatusを確かめ直し、無ければ書かない
- 孤立したベクトルの自己修復: Layer 1でD1に行の無いhit(Vectorizeにはあるのにintentsに無い)を見つけたら、そのidを `deleteByIds` で消す。意思の行は必ずベクトルより先に作られるので、行の無いhitは孤立と判断できる。1回の評価で消す数は `PIPELINE.ORPHAN_DELETE_MAX`(新設・10件)まで。消したことは件数だけをログに出す

## 6. 初期判定の目標と負荷試験の集計(#18)

### 6.1 目標の定義

- 01 §20・02 #33・10 §5の初期判定 p95 10秒は、「保存の時点で、組の相手の意思がVectorizeに反映済みの場合」の、保存から提案の通知の送信試行までとする
- ほぼ同時に預けた組(保存の時点で相手の意思が未反映)の初期判定は、合否を付けない参考値として、Vectorizeの反映の時間と一緒に報告する
- この変更は製品の目標の変更なので、01冒頭の決定記録に「決定内容/根拠/影響」で記録する

### 6.2 負荷試験と集計

- シナリオ(b)を2段にする: 組の片方が先に保存し、その意思の反映(反映確認の行の `processed`)を確かめてから、もう片方が保存する。後から保存した側を「相手が先に反映済み」の標本とする。(b)の所要時間は反映の待ちの分だけ延びる
- 集計(`tools/load/report.mjs`・`lib/queries.mjs`)は、組ごとに相手の反映の時刻と自分の保存の時刻を比べ、「相手が先に反映済み」と「同時」に振り分ける。前者を目標の行、後者を参考の行に出す
- (d)は従来どおり同時の組として扱い、参考の行に出す
