## 1. 全体像

```text
api(POST/PATCH intents)  ※作成・draft→active化は応答の後に同じ要求の続きで第1段・第2段
                         (キューへは60秒遅らせてやり直しの役)/更新は10秒遅延でキューへ
  → Queues(match_events: intent_created / intent_updated)      第1段
      → Embedding計算(07) → Vectorize登録(upsert・反映は待たない)
      → 同じ実行で第2段を続ける(第1段で計算したベクトルを使う)   第2段
        ※第2段の失敗時だけembedding_completedをキューへ送る
          → Layer 2 Candidate Retrieval(Vectorize・topK=100)  ← 実行順は検索が先
          → Layer 1 Hard Filter(コード+D1・通過分から上位K_v=50)
          → Layer 3 Cheap Judge(課金ゼロ・上位K_c=20)
          → Layer 4 Jev(07・予算管理・並列実行)
          → Layer 5 LATCH Engine → 提案化(proposed) → 通知
      → Queues(vector_reflection・遅延付き)                   反映確認
          → 反映を確かめたら第2段を1回だけ評価し直す(30分抑制の例外)

Cron(毎分) → 機会: bucket到来・catch-up / 全Intent: 期限切れ /
             つながり: completed判定 / Embeddingバックフィル /
             未評価回収・遅延再評価(つながり) / 提案クローズ後続(保留昇格・次集合) /
             予算アラート
削除・期限切れ → 即時処理(候補クローズ・ベクトル削除予約。層を経ない)
```

計算量の規律(01 §11): 総当たり禁止。イベント数E×評価対象Kの秩序を維持し、Kは各層の出力上限で頭打ちにする。

## 2. イベントとトリガー

**2段構成。** 作成・更新は第1段でEmbedding計算とVectorizeへのupsertまでを処理し、同じ実行の中でそのまま第2段(Layer 1〜5)を続ける。Embedding完了は`embedding_completed`のmatch_events行として記録し、キューへ送るのは続きの第2段が失敗したときだけとする(下記の第1段から第2段への続行)。埋め込み未完了のIntentは生成元にも対象にもならない。Vectorizeへのupsertの反映には秒から分の単位の遅延があり得るため、**第1段は反映を待たない**(2026-10-22オーナー合意・12 §2の決定記録(評価の流れ))。第1段の順序は、upsert(metadataに意思のversionを含める・05 §2.3)→intentsのembedding_model・embedded_atの更新→反映確認のイベント`vector_reflection`(同version)の遅延付き(2秒)の投入→`embedding_completed`(同version)の行の記録(キューへは送らない)とする。埋め込みの後、upsertの直前に意思の行を読み直し、行が無い・activeでなくなっている・versionが上がっていれば何も書かずに止める(埋め込みの間に削除・一時停止された意思のベクトルを書き戻さない。内容が直された意思は新しいversionのイベントが埋め込む。失敗ではなく処理済みとし、ログpipeline.stage1.skippedを出す・不具合の修正工程(第2回)で確定)。embedded_atの更新も埋め込んだversionのときだけ行い(条件付きの更新)、upsertの間にversionが上がっていたら同じく何も投入せずに止める(embedded_atが別のversionの埋め込みの時刻にならないようにし、次の投入の失敗のやり直しの判定を誤らせない)。第2段はLayer 2 Candidate Retrievalの照会に第1段で計算した自分のベクトルを使う(同じ実行で続けるときはそのまま渡し、続きの第2段の失敗で`embedding_completed`をキューへ送るときはメッセージに載せる。bge-m3の1024次元で約20KB・Queuesの1メッセージの上限128KB以内。match_events行のpayloadには載せない)。反映前でも評価でき、直した意思で古いベクトルを使うこともない。ベクトルの無いメッセージ(旧形式・投入だけのやり直し)はVectorizeから自分のベクトルを読む。第2段は、起点Intentの現行versionと異なる`embedding_completed`を評価せずstale_versionとして処理済みにする(古いversionで評価するとlast_evaluated_atが書かれ、新しいversionの評価が30分の再評価抑制にかかるため)。

**反映確認(vector_reflection・不具合の修正工程で確定)。** 反映前に評価すると、同時に預けた相手のベクトルがまだ見えず、互いを見落とし得る。これを反映確認の評価し直しで拾う。消費のたびに、(1)意思が無い・versionが進んでいる・active以外なら評価せずskipped(not_found・stale_version・inactive)で処理済みにする。(2)自分のベクトルをVectorizeから読み、metadataのversionがイベントのversionと一致すれば反映済みとする(直した意思の古いベクトルを反映済みと誤らない)。(3)未反映で作成から8分未満なら、同じイベントを遅延付きで送り直す。確認の時点は作成から2・6・14・30秒、以後30秒ごととし、送り直しの回数はメッセージに持たず行の作成時刻からの経過で決める(定数はPIPELINE.REFLECTION_DELAYS_S・REFLECTION_GIVE_UP_MS)。(4)未反映のまま作成から8分に達したらfailed(error_code=REFLECTION_TIMEOUT)とし、以後の回収はCron(つながりIntentは(h))に委ねる。打ち切りは実測の反映時間の最大(241.26秒)の約2倍とし、最後の確認は作成から8分30秒より前に終わるため、pending残留の掃査(10分)とぶつからない(2026-10-23オーナー合意・12 §2の決定記録(不具合の修正工程(第2回)))。(5)反映済みなら、評価本体を**30分の再評価抑制の例外**として1回だけ呼び(照会には読んだベクトルを使う)、第2段と同じ計測項目とreflect_ms(§7)をpayloadへ記録して処理済みにする。1回きりはmatch_eventsのUNIQUE(event_type, source_intent_id, version)と処理済みの再消費スキップで保証する。同じ組のJevは同一version組のjev_resultの再利用(§3)で再実行しないため、Jevの呼び出しが増えるのは新しく見つかった組だけで、予算は通常どおり起点側に計上する(§6)。Cronのバックフィル(e)も、第1段の後に反映確認のイベントを投入する(`embedding_completed`は投入せず、評価本体を直接呼ぶ)。**確認の途中の例外(不具合の修正工程(第2回)で確定)。** (2)の読み取りの例外は未反映と同じに扱い、(3)のとおり送り直す(一時的な読み取りの失敗で評価し直しの連鎖を切らない)。(3)の送り直しの送信が例外なら、受け取ったメッセージを同じ遅延でやり直し(行はpendingのまま)、max_retries(3)を超えたものはDLQでdeadになる。(5)の評価の例外はfailedにする。これらはログpipeline.reflection.failed(intent_id付き)に出し、layer(get=読み取り・send=送り直しの送信・evaluate=評価)で見分ける(行がpendingのまま送り直す場合と、failedにする場合を区別できる)。**投入の失敗(不具合の修正工程(第2回)で確定)。** キューの経路の第1段で`embedding_completed`・`vector_reflection`のどちらかの投入が失敗したら、第1段のemitの段の失敗としてメッセージをやり直す(§5)。送れなかったイベントの行は消して「行がある=送れた」を保ち、やり直しの配信は、意思のversionが起点の行と同じで、embedded_atが起点の行の作成時刻以降のときだけ、埋め込み・upsertを繰り返さず、まだ送れていない種別だけを投入する(`embedding_completed`は自分のベクトルを載せずに送る)。やり直しを使い切った場合の評価は未評価の回収(g)が拾う。Cronの経路(バックフィル・修復)は、反映確認の投入の失敗をログだけにする(やり直すメッセージが無く、評価はCronが直後に直接行うため)。

**第1段から第2段への続行(不具合の修正工程(第3回)で確定・オーナー合意2026-10-24・issue #30・12 §2の決定記録(不具合の修正工程(第3回)))。** キューの消費(`consumer.ts`)で第1段が成功したら、`embedding_completed`をキューへ送り直さず、同じ実行の中でそのまま第2段(評価本体)を続ける(キューの受け渡しを1回減らすため)。評価に渡すのは第1段で計算した自分のベクトルで、今のキュー経由の第2段と同じく反映を待たない。`embedding_completed`のmatch_events行は今と同じ形で作り(キューへは送らない)、評価が終わったら今の第2段と同じpayloadを載せて処理済みにする(負荷試験の集計はこの行を使う)。続きの第2段が例外で失敗したら、今と同じ形の`embedding_completed`をキューへ送り、今の第2段の経路(やり直し・DLQ)に任せる。そのキューへの送信も失敗したときは、行をpendingのまま残し、10分の残留の掃査と未評価の回収((g))に任せる。続きの第2段で作られた提案のWeb Pushは、キューの1メッセージの処理の後にメッセージごとの送出(`flushFreshPush`)で送る(04 §4)。反映確認の投入と反映後の1回の評価し直しは変えない。主キューの消費者はmax_batch_size=1とし(オーナー決定3a・04 §4)、メッセージごとに別の実行で並行に処理する(続きの第2段で1件の処理が約5秒に延びるため、バッチの中で後ろの件が待たないように)。

**意思を有効にした要求の応答の後の第1段・第2段(オーナー決定3b・2026-10-24・issue #30)。** 意思を有効にする要求(activeでの作成・下書きの有効化。`intent_created`を投入する2つの経路)は、応答を返した後(`waitUntil`)に、同じ要求の続きでキューの消費と同じ処理(その`intent_created`の行の消費→第1段→同じ実行の第2段→提案の通知の送出)を行う。キューの`intent_created`のメッセージは60秒遅らせて送り(`PIPELINE.INLINE_FALLBACK_DELAY_S`・応答の後の処理の上限30秒より長く、応答の後の処理と重ならない)、やり直しの役にする。キューの消費は、行が処理済みなら何もせず、埋め込み済みなら足りない後続のイベントだけを送る(今の冪等の仕組み)ため、応答の後の処理が済んでいれば何も起きない。第1段が失敗した(起点の`intent_created`の行がpendingのまま)ときは、60秒後に届くキューのメッセージが第1段からやり直す。`embedding_completed`の行を作った後や第2段の途中で止まったときは、起点の行は処理済みのため遅らせたメッセージは何もせず、反映確認の後の評価し直し(30分の再評価抑制を無視する)か未評価の回収((g))が補う。起点の`intent_created`の行は、処理済みにするときpayloadに処理した経路の印`path`(応答の後の処理=`inline`・キュー=`queue`)を載せる(負荷試験の集計で初期判定の行の経路の内訳を出すため。処理は変えない)。第1段の完了のログpipeline.stage1.completedのlayerも、応答の後の処理では`inline`になる。応答の後の処理の例外は応答に波及させず、ログpipeline.inline.failed(error_code・intent_id)だけを出す。応答の後の処理が30秒の上限で第2段の途中に打ち切られたときは、反映確認の後の評価し直しで補われる。環境変数`LATCH_INLINE_PIPELINE`(既定`on`。workerの単体・統合試験の設定では`off`にして、キューを直接呼ぶ今の試験の作法を保つ)。内容の変更(`intent_updated`・10秒遅らせて送る)と再開は今のままキュー経由とする。測っても初期判定がp95 10秒を超えるときの扱いは12 §2の決定記録に従う。

**投入の即時/遅延。** 作成とdraft→active化は、応答の後の処理(上記・`LATCH_INLINE_PIPELINE=on`)で第1段・第2段を行い、キューへは60秒遅らせてやり直しの役として送る(`off`のときは即時投入する。初回提案のレイテンシ優先)。**更新のみ**10秒の遅延配信とし、消費側で起点Intentの現行versionと突き合わせて古ければ破棄する。

**冪等性。** match_eventsのUNIQUE(event_type, source_intent_id, version)が二重投入を許さない。処理済みイベントの再消費はstatus=processedを確認してスキップする。

**Cron(毎分・04 §4)。** (a)機会Intentのbucket到来(starts_atが属する30分Bucket到達の未評価Intent)の再評価、(b)catch-up(expires_atまで2時間以内かつlast_evaluated_atから30分以上経過のactiveな機会Intent)、(c)全active Intentの期限切れバッチ(expired化+ベクトル削除予約)、(d)LATCHのcompleted判定(matchedのつながりLATCHは最終メッセージ(0件ならmatched時刻)から90日経過・matchedの機会LATCHは対象時刻から3時間経過・01 §8)、(e)埋め込み未完了のIntentのバックフィル再試行、(f)usage_counters集計とJev予算アラート(80%)、(g)**埋め込み済みかつ未評価(embedded_at NOT NULL かつ last_evaluated_at NULL)のactive Intentの回収再評価**(キュー消失の安全網)、(h)**active化後10分経過のつながりIntentの1回きり遅延再評価**(upsert反映遅延による相互取りこぼしの安全網。30分の再評価抑制の例外として評価する・§3)、(i)**提案クローズ後続処理**(下記)、(j)**正解データの作成と匿名化**(下記の実装確定(F9・LAT-108))、(k)**Jevの保留の判定し直し**(Jevの障害・予算で保留した候補を、復旧の後に評価し直す。下記の実装確定(不具合の修正工程(第6回)・LAT-105))。

**提案クローズ後続処理。** 提案がクローズ(matched / expired / rejected / cancelled)した時点で、当該ユーザー(機会Intentは当該Intent)の保留candidateを提示順(機会=対象時刻の近い順/つながり=LATCH Score降順)で通知上限までproposedへ昇格し、回答期限を再計算して通知する。グループの「次集合の評価」もこのトリガーで実行する。

**実装確定(F3)。** Cron走査のうち(a)(b)(c)(e)(g)(h)と保持期間削除(05 §2.6の30日定期削除)を毎分Cronで実装する。各走査は評価本体(evaluateIntent)と第1段(Embedding処理)の**直接呼び出し**で完結し、Cronからは新たな起点イベントを発行しない(走査結果をイベント経由にすると再びキューに滞留するため)。走査は1回あたりの処理件数を上限500で頭打ちにし、(status, starts_at)・(status, expires_at)等の索引で対象を最小化する(04 §4)。match_eventsのイベント型のうちintent_expired・intent_deleted・bucket_arrivedはF3では不使用(将来のために予約)。(f)予算アラート・(i)提案クローズ後続処理はF4aで実装済み(次段落)であり、(d)LATCHのcompleted判定はF5で実装済み(下記の実装確定(F5))。

**削除・内容の変更での応答の前後の分担(不具合の修正工程(第3回)で確定・issue #27)。** 意思の削除(DELETE)と内容の変更(PATCH)は、進行中の提案の取り消しを応答の前に終える(候補・イベント行の削除より前に終える必要があるため)。取り消しで空いた枠のための保留の解放と、グループの次の組の提案は、応答の後(`waitUntil`)に行う。保留の解放が失敗しても毎分Cronの(i)が拾い直す。次の組の提案は毎分Cronでは拾い直されず(下記の実装確定(F4b)のとおり全体走査では次集合の評価を行わない)、失敗はログ(latches.next_group.failed)に残る。

**既知の制約(不具合の修正工程(第2回)で記録)。** 次の挙動は、いまの実装で仕様として許容し、ここに書き留める。(1)metadata整合の修復は、点検の対象を並び順も続きの位置も持たない上限500件(CRON_BATCH_LIMIT)で取り出す。対象が500件を超えると点検されない意思が残り得る。500件を超えるのは公開の後のため、そのときに扱う。(2)書き戻しの防止の読み直しとupsertの間には、短い競合の窓が残る(読み直しの直後に削除されると書き戻し得る)。残ったベクトルは自己修復が消す。(3)自己修復はLayer 2 Candidate Retrievalのhit(filterでstatus=active)からしか見つけないため、metadata.statusがpausedの孤立したベクトルは見つからない(検索に現れないため提案には影響しない)。(4)反映確認の処理済みの読み飛ばしは原子的でない。同じメッセージが重ねて配信されると送り直しの連鎖が2本並び得るが、どちらも作成から8分で打ち切られ、提案化は直列化(§3のLayer 5)で守られるため、二重の提案は生じない。(5)Vectorizeの照会は、反映確認が済んだ後でも照会ごとに数十秒から数分古い状態を返し得る(第4回の工程で確認・issue #47)。これは直さず、D1の直近のベクトルの控えで補う(上記)。補えるのは埋め込みから15分以内の意思に限り、それより古い意思は照会に現れるまで待つ。(6)Cronの修復で埋め込み直しても、自分の側の評価し直しは原則として起きない。同じversionの反映確認の行がすでにあるため新しい行は作られず、既存の行が送り直されるだけで、その行が処理済みなら読み飛ばされ、失敗済みなら作成から8分を過ぎているため、最初の確認で未反映ならそのまま失敗になる(送り直さない)。相手の側の評価から見つかることはある(issue #25)。(7)反映を待つ窓の中(有効化から数分)で一時停止すると、状態の同期は何もしない(Vectorizeに自分のベクトルがまだ無く、読み取りが空を返すため)。その後、metadata.statusがactiveのベクトルが反映される。Layer 1がD1の状態で弾くため提案は出ないが、metadataは修復が直すまで(埋め込みから10分を過ぎ、反映確認がpendingでなくなった後の修復の実行まで)activeのまま残る(issue #25)。

**pause/resume。** pauseはVectorize metadataのstatusを即時更新して新規候補化を停止する(進行中の提案は期限どおり継続し、本人は回答可能)。resumeはintent_updatedイベントを発行して再評価する。metadataの即時更新(状態の同期)は、ベクトルが無ければ何もせず、upsertの直前に意思の行を読み直して、行が無い・statusが同期先と違えば書かない(削除の後の書き戻しと、後から来た同期の古いstatusでの上書きを防ぐ・不具合の修正工程(第2回)で確定)。metadata更新の失敗はCronのmetadata整合の修復(次段落)で回収する。

**metadata整合の修復(不具合の修正工程(第2回)で確定)。** 毎分Cronのバックフィル(e)の後に、独立した走査(隔離のlayer=repair)として行う。対象はactive・pausedで埋め込み済み・ベクトル未削除の意思で、Vectorizeから読んで、activeのベクトル欠損は埋め込み直し(`embedding_completed`は投入せず、反映確認だけを投入する。pausedの欠損は新規候補化の対象外のため放置する)、metadata.statusの不一致は同じベクトルの値で現行のstatusへ書き直す。反映待ちの意思は点検しない。すなわち、埋め込みから10分を過ぎた(ちょうどを含む)意思だけを点検し(PIPELINE.REPAIR_GRACE_MS)、その意思の現在のversionの反映確認の行がpendingなら経過によらず点検しない(第1段はupsertの反映を待たずにembedded_atを書くため、反映前のベクトル不在を欠損と誤って埋め込み直さない・issue #13・#21)。除外の長さは反映確認の打ち切り(8分)とは別の値として持ち、打ち切りを変えても除外が縮まないようにした。Vectorizeの読み取り(getByIds)は1回20件までのため(PIPELINE.VECTOR_GET_MAX)、Vectorizeの実装の中で20件ずつに分けて呼ぶ(修復・群評価・反映確認の呼び出し側は上限を意識しない・issue #15)。statusの書き直しは、upsertの直前に意思の行を読み直し、行が無い・statusが点検の時点と変わった意思は書かない(次の実行で点検する)。

**つながりIntentはbucketを持たない。** 再評価は新規・更新Intentを起点とする候補検索と(g)(h)の安全網、Jevの保留の判定し直し(k)で完結する。catch-up・bucketは機会Intentのみ。

## 3. 5層の仕様

### Layer 2 Candidate Retrieval(Vectorize・実行の最初)

起点Intentの正規化テキスト(07 §4)をクエリとして、`filter={form, status:"active"}`付きでANN検索する。**取り出し幅はtopK=100(プラットフォーム上限。1クエリの上限を超える取得・ページングは存在しない)**。filterは最適化であり、取り出し後の判定はLayer 1が担う。**照会の直後に、直近のベクトルの控え(`recent_vectors`・05 §2.2)から補う(不具合の修正工程(第4回)で確定・issue #47・§2)。** 同じform・status=active・控えのembedded_atがintents.embedded_atと一致する(現在の版の)・自分以外・埋め込みから15分以内の行を新しい順に最大50件(`RECENT_VECTOR_SUPPLEMENT_MAX`)読み(このとき、Layer 1で必ず不合格になる相手=起点と同じ利用者(self_pair)と、機会Intentどうしで時間の重なりが15分未満の相手(time_no_overlap・Layer 1と同じ式で終端はends_atが無ければexpires_at・どちらかの開始か終端が無く判定できない相手は除かない)を先に除き、50件の枠を見込みのある相手に使う。Layer 1の判定の結果は変わらない・不具合の修正工程(第5回)で確定・LAT-99)、照会の結果に既にあるidを除いて、起点とのコサイン類似度(Vectorizeと同じ尺度)で照会の結果と合わせて降順に並べ、topK=100で切る。次元のずれる行は読み飛ばす。控えの読み込みは2段に分ける。照会と同時に投げるのはintent_idとembedded_atだけの読み込みで、vectorは照会の結果に無いidがあるときだけ、そのid(最大50件)の分を2回目に読む(D1のJSのAPIはBLOBを数値の配列で返し1行約15KBになるため、照会の結果に既にある相手の分まで毎回読むと評価1回あたり約0.75MBになる)。1回目の後に控えが上書き・削除された行は使わない。読み込みの失敗は補い無しで続ける(ログpipeline.recent_vector.failed)。以降のLayer 1〜は従来どおりで、補った行はD1に意思の行があるため孤立したベクトルの自己修復の対象にならない。

### Layer 1 Hard Filter(コード+D1 — AI不使用)

取り出した候補(最大100件)と起点Intentの組ごとに、次を**コードで**判定する。出力はpass/failのみ。**Vectorize metadataに依存せず、status・ブロック・履歴はD1の現行値で再検証する**(二重化)。D1への照会はチャンクで分割して発行する(実装確定・F3): 候補Intentの一括取得とbirth_date取得は**100件チャンク**、blocks・proposal_historyの照会は**48件チャンク**(両方向のor+outcomeのinを含む1文のバインド数がD1の上限100内に収まる値)。

| 判定 | 規則 | データ |
|---|---|---|
| form一致 | 双方のformが同一(つながり×機会は絶対不合格) | Vectorize filter+D1 |
| status | 双方active(D1現行値) | D1 |
| 自己ペア | user_id一致は不合格 | コード |
| ブロック | いずれかの方向のblocks行の存在 | D1 |
| 提案履歴 | proposal_historyにoutcomeがmatchedまたはrejectedの行の存在(恒久排除・01 §8裁定) | D1 |
| 飲酒年齢 | 機会×alcohol_involved=true は**判定時点で**両者満20歳必須(作成時と候補化時の双方で検証・08 §8) | D1 |
| 時間(機会のみ) | 開始・終了の重なりが15分以上。ends_at=nullはexpires_at(既定start+3時間)を終端とみなす | D1(intents) |
| 地域(両方添付時のみ) | bbox事前絞り+中心間距離 ≤ 半径の和 | D1+TS計算 |
| 人数 | participants区間の共通部分あり(2〜4人内) | コード |
| 予算(機会のみ) | 区間の共通部分あり | コード |

地理を片方しか添付していない組・双方未添付の組は地理判定を行わない(全国スコープ・01 §12)。判定データを欠くNG条件はSoft Constraint側(01 §5)であり、本層では扱わない。照合時にD1行が存在しない候補はfail-closeで除外し、そのベクトルは削除の後に残った孤立したベクトルとして消す(1回の評価で10件まで・§2の孤立したベクトルの自己修復・不具合の修正工程(第2回)で確定)。

Layer 1通過後、**類似度上位K_v=50**を次層へ渡す(同点はULID昇順)。

### Layer 3 Cheap Judge(LLM不使用・課金ゼロ)

1対1候補の安価な事前順位付け。合成スコア= `0.7×正規化類似度 + 0.3×ルール点` とする。ルール点は (a)topic語彙の一致度(文字一致率) (b)participants区間の重なり幅 (c)地理添付時の中心間距離の近さ(未添付は中立値)、の3要素の等分。topic語彙の一致度は、双方のtopicが空(未確定)の場合は**1(同一扱い)**・片方のみ空の場合は0とする(F3実装確定)。**上位K_c=20**をLayer 4へ渡す。LLMをここに使わない理由は、コスト保護3層(04 §5)の実効性を保つため(課金発生はJev・Parser・Embeddingに限る)。

### Layer 4 Jev(07のAPIを予算内で実行)

- 実行回数上限: **1イベント処理あたりK_j=8回**(実API呼び出しごとに計上。フォールバック呼び出しも計上)。**8回は並列実行する**(直列では初回判定の10秒目標を超える)
- 配分: 1対1候補に**最低4回を保証**、残りをグループ構成ペアに割当(グループ候補がなければ1対1へ繰上げ)。**残り予算で必要ペア数(C(n,2))を判定しきれないグループ候補は部分評価を採らず保留する**(次イベントまたはjev_result再利用で完結後に提案化)
- 対象の順: Layer 3スコア降順。上限到達で残りは保留(candidateのまま)
- **実装確定(F4a)。** K_j=8は実呼び出し(フォールバックを含む)の枠である。各波の前に、その波で呼ぶ件数nぶんの予算を4つのカウンタへ1回のdb.batchでまとめて加算して予約し(reserveJevCalls。呼べる件数は、nと、各カウンタの「上限−加算前の値」の最小(0未満は0)の小さい方。nに満たないときは、尽きた1件も試行として数える従来の規則に合わせ、加えすぎた分を1回のdb.batchで引き戻す。1件ずつ確保した場合と同じ件数・同じカウンタの値になる・不具合の修正工程(第3回)・issue #39でD1への問い合わせを減らすために確定)、予約できた件だけを並列実行する(予算到達・circuit breakerのオープン・失敗・枠超過の分は保留として数える)。予算は**起点側(イベントを生じたIntentとそのユーザー)のみ**に計上する(相手側の予算を他人の行動で消費させないため・§6)。1対1への最低4回保証の配分はF4bで実装した(次項)。提案履歴により現時点で提案できない相手(既存行があり再提案不可=つながり・機会でdeferred/expired以外、または機会の再提案の抑制期間中)はLayer 4へ渡さず、Jevの枠と予算を使わない(除外件数はpayloadのl4_skipped_history・§7)。この除外はLayer 1の恒久排除(matched・rejected)とは別に数え、提案化の時点の履歴判定も並行時の正として残す。照会は相手ユーザー48件のチャンクで行う。Jevの呼び出しが例外を投げた場合は失敗種別otherとして扱い(フォールバック対象外)、予約済みの実行を含む評価全体を失敗させない
- **実装確定(F4b)。** 人数の条件: 人数nの提案は、nが全メンバーのparticipants区間[min, max]に入るときだけ作る。1対1(n=2)にも適用し、双方のparticipants.minが2でない候補(どちらかがmin≥3)は1対1のLayer 4へ渡さず、Jevの枠と予算を使わない(除外件数はl4_skipped_participants・§7。Layer 1の人数判定=区間の共通部分は従来どおり)。配分: 1対1の対象(提案履歴で除外されず人数の条件を満たす候補・Layer 3降順)のうちjev_resultの無い件数をN₁とし、グループの枠を 8 − min(4, N₁) とする。集合を安価な順位(Layer 5)の上から見て、jev_resultが無くまだ予定に入っていないペアの数が残りの枠に収まる集合だけを予定に入れ、収まらない集合は部分評価せず保留する(group_held_sets)。1対1には 8 − 予定に入れたグループのペア数 の枠を、未判定の対象のLayer 3降順に割り当てる(1対1の未判定分は最低min(4, N₁)回が保証される)。起点を含むペアが1対1の対象と重なる場合は1対1側の対象として1回だけ数え、共用する(二重に呼ばない)。グループ候補が無ければ8回すべてを1対1に使い、1対1の対象が4件未満なら余りをグループへ回す。1対1とグループの予定は1つの対象列(1対1を先・グループを後)にしてJevを1回だけ実行し、予算・circuit breaker・並列・フォールバックは共通部のまま起点側のみに計上する。集合を構成する他人どうしのペアもmatch_candidatesへupsertし(a<b正規化・現在のversion組・retrieval_score=Pool全員のベクトルのコサイン類似度・cheap_judge_score=Layer 3と同じ式)、jev_resultとlatch_score(Jev値・H=1)を保存して次のイベントで再利用する(保留した集合はこれで完結できる)
- 1ペア=1リクエスト(7軸を並列評価・07 §5)
- **jev_resultの再利用**: 同一バージョン組(両Intentが未更新)のmatch_candidates既存行にjev_resultがあれば再実行しない。30分再評価抑制(intents.last_evaluated_at)は別規則として併用する。ただしactive Intentの意味フィールド(topic・time・geo・participants・budget・constraints=intent_updatedを発行する変更・§2)の更新ではlast_evaluated_atをnullへ戻して抑制を解除する(表示系だけの変更では解除しない。オーナー裁定 2026-10-20・05 §3.3)。抑制は同じ内容の繰り返し評価を防ぐためのもので、条件変更で進行中の提案が取り消された直後の再提案を最大30分遅らせないためである。**抑制の例外(不具合の修正工程で確定)。** 反映確認の評価し直し(§2)とCronの(h)の遅延再評価は、抑制にかからず評価する(どちらも1回きりで、埋め込みの直後の評価に抑制されると取りこぼしの回収が空振りになるため)

### Layer 5 LATCH Engine

- H(Hard Constraint)の最終再検証(判定時点で条件が変わっていないか。**提案履歴の存在判定を含む**)を経て、`L = H × min(P(a→b), P(b→a)) × C`(C初期値1)を算出
- **L > 0.60(初期値)で提案化(proposed)**。閾値未満はcandidateのままシステム内部データ
- **実装確定(F4a)。** match_candidates.latch_scoreはJev値(H=1とした値)で保存し(閾値未満も保存する)、Hの最終再検証の不合格は「提案しない」で表す(スコアを0で上書きしない)
- **提案化はユーザーペア単位で直列に実行し、proposal_historyへの追加成功(UNIQUE)を提案化の完了条件とする。** 同一イベント処理で同一ユーザーペアの複数候補が閾値を超えた場合は、LATCH Score最大の1件のみ提案化し、残りはcandidate保持とする
- **提案化の直列化(F4a実装確定)。** proposal_historyの確保を1文目に置き、後続(latches・latch_members・latch_status_events・候補のstatus・通知)の各文を「proposal_historyにlatch_id=新LATCHの行が存在すること」(EXISTS)で条件付けた1つのD1バッチ(トランザクション)で書く。確保は、新規ペアは `INSERT … ON CONFLICT DO NOTHING`、再提案(§4)は `outcome IN (deferred, expired) AND updated_at=読み出し値` を条件とするUPDATE(楽観照合)とする。確保に失敗すれば後続はすべて0行となり何も残らない。proposal_history.latch_idの外部キーをコミット時の検査とするため、バッチ先頭で `PRAGMA defer_foreign_keys = ON` を実行する。再提案の可否(抑制期間・スコア変化・Intent更新)は読み出した値でコードが判定し、書き込み時の照合で並行更新を退ける。**提案直前のブロックの照合(F7a実装確定)。** 後続の各文の条件(確保の存在)に「参加者のどの2人の間にもblocks行が無いこと」を加え(グループは全ペア)、満たさなければLATCHを作らず、同じバッチ末尾の補償文で確保を巻き戻す。ブロックのAPIはblocks行を先に書いてから進行中の提案を取り消すため(05 §3.3)、D1の書き込みの直列化により、評価の開始後にブロックされた組でもどちらの順でもブロック後に提示が残らない
- グループ(3〜4人): Layer 1通過済の近傍から**Pool最大15**を構築(同一form・主題近接・participants整合)。全ペアのMutualScoreの最小値をaggregateとし、貪欲法で集合を選ぶ(aggregate降順・同点は小集合優先・さらにULID辞書順)。**通知は1集合のみ**。次集合の評価は提案クローズ後続処理(§2)で行う
- **実装確定(F4b)。** Pool: 起点のparticipants.max≥3のときだけグループを組み立てる(parserの既定{min:2, max:2}のIntentは1対1のみ)。Layer 1通過後の上位K_v=50からparticipants.max≥3の候補を選び、起点との安価な順位付けの点数(Layer 3の合成スコア)の降順・同点はULID昇順で最大15件をPoolとする(ベクトルの無い候補は他人どうしの類似度を出せないため除く)。Pool内の起点以外どうしの組にも、Layer 1と同じHard判定(ブロック・恒久排除・飲酒年齢・時間の重なり・地域・人数・予算・自己ペア)と提案履歴による事前除外(Layer 4と同じ規則)をかける(D1照会はPool全員分をまとめ、blocks・proposal_historyは48件チャンク)。時間・予算の全員の共通部分は別に判定しない(区間は「全ペアが重なれば全員の共通部分も同じ幅以上ある」性質を持つ。共通部分は開始が最も遅い人と終了が最も早い人の2人の重なりと一致する)。集合: 起点を含む3人・4人の組み合わせ(最大C(15,2)+C(15,3)=560通り)のうち、全ペアがHard判定を通り、人数nが全員の区間に入るものを有効とする。安価な順位は全ペアの安価な点数の最小値の降順(同点は小集合優先・さらにメンバーのULIDを昇順に並べた文字列の辞書順)で、この順にJevの配分(Layer 4)にかける。点数: 全ペアのjev_resultが揃った集合だけaggregate=全ペアのLATCH Score(min(P(a→b), P(b→a))×C)の最小値を出してgroup_candidatesへ保存する(05 §2.2)。選択: aggregate > 0.60の集合をaggregate降順・同点は小集合優先・さらにULID辞書順に見て、提案の直前に全メンバーのHをD1の現行値で再検証し(起点の読み直しと全員のversionの照合を含む。1人でも違えば次の集合へ)、提案化する。**1回の評価で提案する集合は1つだけ**で、提案化が履歴の確保に失敗したら次の集合を試し、提示または保留になった時点で止める(1対1の提案化の後に行う)。集合のlatches.scoreはaggregateとし、保留の解放の順序(つながり=score降順)も同じ値で並べる。提案化は全ペア(C(n,2)行)のproposal_historyの確保を1バッチの先頭に並べ、確保数がC(n,2)未満のときだけ働く補償文を同じバッチの末尾に置いて半端な確保を残さない(新規INSERTした行は削除・UPDATEした行は読み出した値へ戻す)。提案内容の主題・地域の基準は最初に預けられたIntent(created_at最小・同値はid昇順)、time_window・participants・budgetは全員の区間の共通部分とし、回答期限の対象時刻は全員のstarts_atの最大値・Intent期限は全員のexpires_atの最小値とする(§4の式のまま)。提示か保留かは全メンバーについて通知上限(§4)を判定し、1人でも上限なら保留する。グループ部分(Pool構築〜集合の提案)の例外は1対1の評価と提案を止めない(ログpipeline.group.failedとpayloadのgroup_failed・§7)

## 4. 提案化と通知

**回答期限の導出。** 機会= `min( max(通知+15分, min(通知+2時間, 対象時刻−60分)), 参加Intent期限の最小値 )`。つながり= `min(通知+24時間, 参加Intent期限の最小値)`(01 §8)。対象時刻まで75分を切った機会提案は通知しない。

**通知の上限と保留。** 1ユーザー1日6件・1Intent同時進行3件。超過分は破棄せず保留(candidate保持)。提示順は**機会=対象時刻の近い順/つながり=LATCH Score降順**(01 §10)。保留の解放は提案クローズ後続処理(§2)が担う。提示時に回答期限を再計算する。**上限の判定と通知の書き込みは同一文ではないため、並行消費で上限を1件程度超え得る(許容・F4a実装確定)。** **評価(§3)が作る提案の通知の行(1対1・グループ)のcreated_atは、評価の開始時刻でなく提案を作る直前の時刻とする(提案の行・回答期限・提案履歴は評価の開始時刻のまま。01 §20の「通知は判定後5秒以内」の起点を判定の終わりに揃える・不具合の修正工程(第5回)で確定・LAT-98)。** 評価の開始とJSTの日付の変わり目をまたぐときは、上限は評価の開始の日で判定し、通知は作った日の件数に入る(上の1件程度の超過の範囲)。 重複通知の防止として、通知ステップの前にlatch.statusを再確認し(proposed反映済みなら送信スキップ)、notificationsはUNIQUE(latch_id, user_id, type)で保護する。**Web Pushの送出(F7b実装確定)。** 通知行のうちproposal(提示・保留の解放)とmatched(成立)は送信の状態push_state=pendingで書き、主キューのバッチの後(DLQは除く)とLATCH・Intent・安全のAPIの変更系の応答の後に、同じWorker内で送出する(waitUntil・2026-10-21オーナー裁定・04 §4)。送出の失敗はキューの消費とAPIの応答に影響させず、送れていない行はCronの回収走査(§2)が拾う。毎分Cronが評価本体を直接呼んで作った通知((a)(b)(e)(g)(h)・保留の解放・次集合の提案)は、それらの走査の後に、その回のCronの開始以後に作られたpending行をその実行の中で送る(30秒以上たった行を拾う回収走査は送り損ねの安全網として残す。他の走査と隔離する・issue #9・不具合の修正工程で確定)。主キューの消費では、1件のメッセージの処理で通知が作られたら、バッチの終わりを待たずにその場で送出を始める(対象はそのメッセージの処理の開始以後に作られた通知。長いバッチの先頭で作った提案のWeb Pushが最後まで待たされない・issue #19・不具合の修正工程(第2回)で確定)。バッチの後の送出は取りこぼしの回収として残し、二重の送信は順番取り(1文の条件付きUPDATE・04 §4)で防ぐ。入口・応答の後の処理(削除と内容の変更)・主キューの実行の最後の送出は、対象をその要求・処理・実行の開始以後に作られた通知に限り、それより前の未送信は毎分Cronの回収が送る(issue #39・不具合の修正工程(第3回)で確定)。主キューのバッチの待ち(max_batch_timeout)は1秒とする(04 §4)。notification_level=mutedの参加Intentを持つ本人にはWeb Pushを送らず、アプリ内通知の行と通知上限の数え方は変えない(01冒頭の決定記録(2026-10-21・通知のAPI))。

**反映を待つ提案(不具合の修正工程で確定)。** 同時に預けた2人の提案は、先に評価した側から相手がまだ見えないとき、反映確認の評価し直し(§2)で作られる。このとき提案はVectorizeの反映にかかった時間だけ遅れる(反映の時間はreflect_ms・§7)。評価し直しは30分の再評価抑制の例外(§3)であり、通知上限・保留・回答期限の規則は通常の評価と同じに当てる。

**同時通知・開示。** 必要人数全員へ同時通知。不成立時の開示は「この提案は成立しませんでした」の一文のみ。

**同時YES(F4a実装確定)。** 回答の記録・状態遷移の記録・状態の更新を1つのD1バッチで行い、YES数をDB内で数えてmatched/partial_acceptを決める(並行するYESの取りこぼし・二重遷移を防ぐ)。機会LATCHのyesには「参加Intentにmatchedが無い」条件を加え、成立時の参加Intentのmatched化も同じバッチ内で行う(同一機会Intentの二重成立を防ぐ・02 §4の#23)。

**排他(機会のみ)。** あるIntentのLATCH成立時点で、そのIntentを含む回答待ち提案はすべてcancelled。つながりは排他なし(成立後active復帰・複数成立可)。

**提案履歴と再提案(01 §8裁定)。** 提案の生成にはproposal_historyの追加を伴う。恒久排除は**outcomeがmatched(成立)またはrejected(明示の拒否no)の履歴**だけで行う。deferred(見送り)・expired(回答期限切れ)の履歴は排除対象とせず、機会Intentに限り、見送り後 min(24時間, 対象時刻までの残時間の半分) の抑制期間を経て、スコア変化またはどちらかのIntent更新を条件に再提案する(prev_latch_scoreとの比較でスコア変化を判定)。抑制期間の基準はproposal_history.updated_at(見送り・期限切れの時刻)とし、「Intent更新」はどちらかのIntentのupdated_atが前回LATCHのcreated_atより後であることで判定する(updated_atはversionと同時に進む・F4a実装確定)。つながりIntentへの再提案は行わない(提示された提案についての規則)。**未提示・システムの都合で閉じた提案は履歴を消費しない(オーナー裁定 2026-10-20・F4a実装確定)。** 一度も提示しないまま閉じた保留(保留中の期限切れ・機会で対象時刻まで75分を切ったもの・参加Intentの終了)と、機会の排他・Intent削除・意味フィールドの変更(Hard Constraintの変化)で閉じた提案は、そのLATCHのために新規に確保したproposal_history行を削除してペアを未提案に戻し、再提案で確保した既存行はexpiredに戻す(05 §2.2)。提示後の回答期限切れ・defer・noは従来どおりexpired / deferred / rejectedを記録する。**グループ提案が回答期限までに必要人数に届かなかった場合はexpiredで閉じ、既存のYESは無効(次提案に持ち越さない)。**提案履歴は有効なyesを持たない参加者を含むペアだけをexpiredで記録し、yesどうしのペアは消費しない(オーナー裁定 2026-10-20・01冒頭の決定記録・F4b実装確定)。グループ提案がdefer / noで閉じた場合は、閉じた本人を含むペアだけをdeferred / rejectedで記録し、本人を含まないペアは消費しない(同裁定。ペア別の記録の一覧は05 §2.2)。再提案の可否はペアごとに上記の規則を当て(1ペアでも再提案不可なら集合を提案しない)、スコア変化はペアの既存行が指す前回LATCH(1対1・集合を問わない)のscoreと今回の点数で判定する。1つのペアは同時に1つの進行中LATCHにしか属せないため、1対1の提案が進行中のペアを含む集合は、その提案が閉じるまで提案されない。恒久排除はペア単位であり、1対1で成立(またはno)したペアを含む集合は以後作られない。

## 6. コスト保護(3層)と予算計上

API源流レート制限・Jev予算(1Intentあたり1日40回・1ユーザーあたり1日120回・30分抑制(意味フィールドの更新で解除・反映確認の評価し直しと(h)は例外・§3))・実行回数上限(1日30,000回・1か月600,000回・80%アラート)は04 §5の表どおり、usage_countersで実装する。**実API呼び出し(フォールバック切替を含む)をすべて計上する**規則を適用する。1Intentあたり・1ユーザーあたりの予算は**起点側(イベントを生じたIntentとそのユーザー)のみ**に計上する(相手側の予算を他人の行動で消費させない・F4a実装確定)。確保は1回の波(Jevを並列に呼ぶ単位)につき、4つのカウンタへの加算を1回のdb.batchにまとめる(§3のLayer 4・issue #39)。

## 7. 観測(Analytics Engine+D1集計)

各層の通過件数(Vectorize取得→L1通過→L2確定→L3通過→Jev実行→提案化)と**Layer 1の除外理由別内訳**・Jev回数/latency/費用・LATCH Score分布・提示数・回答率・保留→expired率・**Embedding未完・未評価の滞留件数**・DLQ件数を、イベント単位で記録する。02の#35(Analytics)・#7(総当たり禁止の観察)・#11〜#13/#26(非生成の証明)の証拠はこの計測が担う。

**#35の集計(F9で確定・LAT-82)。** 02 #35の6つの数値は、D1の記録(match_eventsのpayload・usage_counters・match_candidates・latches・latch_responses・latch_status_events・messages)への読み取りの問い合わせで出す(集計のコマンド`pnpm analytics:report`・数え方は09 §2)。毎分Cronが評価本体を直接呼ぶ評価はpayloadへ書かれず(下記)、削除した意思のmatch_eventsの行は消える(05 §2.5)ため、D1の候補数はこれらを含まない。全量はAnalytics Engineのdata pointにある(09 §2のオーナー決定)

**実装確定(F3)。** 第2段(評価)の結果は、起点イベント(embedding_completed)の行のmatch_events.payloadへ記録する。記録するのは層通過件数(retrieval_count / l1_pass / l1_exclusions(Layer 1の除外理由別内訳) / l3_pass)と処理済み判定の理由(抑制・対象外はskipped理由・旧versionはstale_version)であり、raw_text・座標は格納しない(05 §2.5)。あわせてAnalytics Engine(dataset=latch_metrics・バインディング=PIPELINE_AX)へ層通過のdata pointをイベント単位で書き、処理結果は許可リストの構造化ログ(04 §4)に出力する。バインド未設定の環境(単体試験等)では送信を省略し例外を出さない。

**実装確定(不具合の修正工程(第4回)・issue #47)。** payload(retrieval_count=Layer 2 Candidate Retrievalの照会が返した件数は従来から記録)へ、控えから補った件数(supplement_count)を加える。評価の完了のログpipeline.stage2.completedにも、retrieval_count(補いを含まず、自idの除外の前)とsupplement_countを出す。ログの許可リスト(08 §6)へ同名の2項目を足した。段ごとの所要時間のログ(pipeline.stage2.timing)には、控えの読み込みの残りの待ちの段supplementが加わる。Analytics Engineのdoublesには入れない(数値の上限・下記)。負荷試験で、補いが初期判定につながった件数を確かめるために使う。

**実装確定(F4a)。** payloadにJev・提案化の項目を加える: l4_skipped_history(提案履歴により提案できずLayer 4へ渡さなかった件数・§3) / jev_calls(実呼び出し回数) / jev_reused(jev_resultの再利用件数) / jev_held(保留の理由別内訳=budget・breaker・failed・cap) / jev_latency / l5_over_threshold(L>0.60の件数) / proposed(提示した件数) / held_proposals(通知上限で保留した件数)。#14・#15の証拠はこの記録とmatch_candidates.jev_resultが担う。

**実装確定(F4b)。** payload(とAnalytics Engineのdata point)にグループの項目を加える: l4_skipped_participants(人数の条件で1対1のLayer 4へ渡さなかった件数・§3) / group_pool(Poolの件数。グループを組み立てない・グループ部分の失敗では0) / group_sets(列挙で得た有効な集合の数) / group_jev_calls(グループのペアとしてJevへ渡した件数。1対1の対象と重なるペアは1対1側で数える) / group_held_sets(判定しきれず保留した集合の数=配分の枠に収まらなかった集合+Jevの判定が欠けた集合) / group_over_threshold(aggregate>0.60の集合の数) / group_proposed(提示した集合の数=0または1) / group_held_proposals(通知上限で保留した集合の数=0または1) / group_failed(グループ部分で例外が起きたら1)。jev_reusedはLayer 4へ渡した行のうちjev_resultを再利用した件数だけを数える(集合の点数の計算で既存のjev_resultを読む分は数えない)。#24の証拠はこの記録とLATCH・提案履歴の観測(05 §3.3のdev専用API)が担う。

**実装確定(F8b)。** payload(とAnalytics Engineの`stage2`のdata pointの最後の数値)にLayer 2 Candidate Retrievalの所要時間を加える: retrieval_ms(Vectorizeへの問い合わせ(topK=100・§3)の所要時間・ミリ秒)。所要時間は処理時間の計測であり時刻依存のロジックではないため、Clockではなく`performance.now()`の差で測る。Cronが評価本体を直接呼ぶ経路(§2)では、payloadへは書かれずAnalytics Engineのdata pointにだけ載る。負荷試験(02 #33・10 §5)のCandidate Retrieval p95 1秒の集計はこの値を使う。D1の形は変わらない(マイグレーションは無い)

**実行ごとの計測の書き込みの残り(不具合の修正工程(第3回)で確定・issue #28)。** Analytics Engineの書き込み(`writeDataPoint`)は1回の実行(fetch・queue・scheduled)あたり250件までで、評価1件が2件(`stage2`・`stage2_group`)を書くため、毎分Cronが1回に125件を超えて評価すると後ろの書き込みが失敗した。そこで1回の実行ごとに書き込みの残り(`PIPELINE.METRICS_WRITES_PER_INVOCATION`=240件・上限250件の手前)を持つ小さな部品を実行の入口で作って評価へ渡す(isolateは複数の要求を同時に扱うため、モジュールの変数では数えない)。評価の2件組は2件とも書けるときだけ書き(片方だけにしない)、残りが足りなければ書かず、その実行で1回だけ警告ログpipeline.metrics.skipped(書かなかった件数)を出す。毎分Cronは、予算アラートの書き込み2件を先に確保し、評価に使う残りを238件にする。match_events.payloadの記録は変えない(負荷試験の集計はこちらを使う)。

**第2段の段ごとの所要時間(不具合の修正工程(第3回)で確定・issue #30・#36)。** 第2段の所要時間の内訳を、ログpipeline.stage2.timing(intent_id・layer=段の名前・latency)に段ごとに出す(許可リストの項目は増やさない)。段はprepare(意思の読み込み・30分抑制の判定・自分のベクトルの取得)・retrieval・layer1・layer3・candidates・group・jev_pre・jev_call(内訳としてjev_breaker・jev_reserve・jev_http(外部送信の集計の書き込みを含む)・jev_record)・jev_post・layer5・propose・finishである。Lの保存は、提案があるときはproposeの段に、無いときはfinishの段に入るため、layer5はほぼ0になる。時刻は処理時間の計測のため実時間で測る。D1の問い合わせの待ちが大きいため(キューの処理からは1回約0.12秒)、互いに依存しない問い合わせは同時に投げるか1回のbatchにまとめる(提案化・提案直前の再検証・候補の保存・Layer 1の読み込み。結果と順番の保証は変えない)。

**実装確定(不具合の修正工程)。** Analytics Engineの1つのdata pointは数値(doubles)を20個までしか持てず、超えると書き込みが例外を投げて評価全体が失敗する(issue #8。F4bの項目とF8bのretrieval_msで24個になっていた)。第2段の記録はイベントごとに2件のdata pointに分ける: `stage2`(文字列=処理段の識別・Layer 1の除外理由別内訳。数値=層通過件数(Vectorize取得→L1→L3)・処理時間・Jev(呼び出し・再利用・保留の理由別4項目・処理時間)・L5閾値超過・提示・保留・retrieval_msの15個)と、`stage2_group`(数値=F4bのグループの9項目)。反映確認(§2)のmatch_events行のpayloadには、評価し直した結果の第2段と同じ項目と、reflect_ms(反映確認のイベントの作成から反映を確かめるまでのミリ秒)を記録する(評価しなかったときはskipped=not_evaluatedとreflect_ms)。reflect_msは負荷試験の集計(10 §5)で本物のVectorizeの反映時間の参考値として使い、01 §20に目標値は無いため合否は付けない。D1の形は変わらない(event_typeはCHECK制約の無いTEXT列のため、`vector_reflection`の追加にマイグレーションは要らない・05 §2.2)

**実装確定(不具合の修正工程(第2回))。** 第2段の2件のdata pointの文字列(blobs)を次の並びにする: `stage2`=処理段の識別・Layer 1の除外理由別内訳(JSON)・評価の起点(origin)・結合の鍵、`stage2_group`=処理段の識別・評価の起点(origin)・結合の鍵(数値の並びは変えない)。評価の起点は`embedding_completed`(キュー経由の即時の評価)・`vector_reflection`(反映確認の評価し直し)・`cron_backfill`(バックフィル(e))・`cron_delayed`(遅延再評価(h))・`cron_jev_held`(Jevの保留の判定し直し(k)・LAT-105で加えた)・`cron_other`(その他のCronの評価=(a)(b)(g)。起点を指定しない呼び出しの既定)で、即時の評価と評価し直し・Cronの評価を計測の上で見分ける(issue #24)。結合の鍵は1回の評価の2件のdata pointを結ぶために評価ごとに作る乱数で、どこにも保存しない(イベントのidや意思のidは載せない・08 §6)。data pointの書き込みの例外(上限の超過等)は評価をfailedにせず、ログpipeline.metrics.failedだけを出す。原因の切り分けのため、ログのerror_codeは例外の分類名にする(例外のcauseを辿り、Vectorize=`VECTOR_<操作>_<符号>`・D1=`D1_OVERLOADED`/`D1_ERROR`・Queues=`QUEUE_SEND_FAILED`・Workers AI=`AI_<符号>`・その他は例外の型名、判定できなければ従来の符号。例外の文の中身は出さない)。あわせて、第1段の完了のログ(pipeline.stage1.completed)のlayerに第1段を呼んだ経路(queue・backfill・repair)を、書かずに止めたときのログpipeline.stage1.skippedのlayerに同じ経路を、意思の削除APIの段ごとの所要時間をログintents.delete.timing(layer=vector・d1・latency)に出す。ログの許可リストの項目は増やさない(04 §4)
