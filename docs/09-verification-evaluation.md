## 2. 成功指標の測定定義

**North Star: Mutual Latch Rate。** 分母=当該期間に通知を送信した提案数(1提案1計上・グループも1提案。期限切れ・no・cancelled(競合を含む)を除かない)。分子=必要人数全員がyesした提案数。**形式別(つながり/機会)の内訳を必ず併記する。**集計はlatch_status_eventsの日次バッチ(D1)。

**主要KPI(4群・01 §23)**

| 群 | 指標 | 定義の要点 |
|---|---|---|
| 使われ方 | Intent作成率/再作成率/Active数/7日・30日継続率 | 分母=セッション開始ユーザー(sessions表) |
| マッチングの質 | Candidate生成率/提示率/保留→expired率/YES率/MLR/無回答率 | 06 §7の計測から日次集計 |
| つながりの品質 | チャット開始率(成立後7日以内に双方1件以上送信)/往復継続率(30日)/ブロック率/1つながりIntentの成立数 | messages・chat_reads・blocksから集計 |
| コスト | 1IntentあたりJev実行数/1成立あたりLLM費用 | usage_counters+費用記録 |

## 3. ゴールドセット

- 日本語・両形式混在。規模: 各form 40件以上+境界20件以上(form曖昧・alcohol暗示表現・地域のみ添付・人数のみ添付)
- 形式: YAML(入力文・期待値の全フィールド)・リポジトリ管理・変更はレビュー制
- 利用: Parser/Embedding/JevのOffline評価(§4)とCIのstub参照
- **置き場所と形式(LLM real接続で確定)**: リポジトリ直下の`eval/goldset/parser.yaml`(Parser用: 入力文・相対日時の基準の現在時刻・期待値)と`eval/goldset/jev-pairs.yaml`(Jev用: 2つの意思の構造化データ(正規化の関数に通すもの)・手で付けた正解yes/no・任意の地域名`area`)。形式の説明は`eval/goldset/README.md`。先頭に`version`(整数)と`approved_by_owner`(承認日またはnull)を持ち、nullの版で採点した記録は合格として扱わない。期待値には採点する項目だけを書く(書かない項目は採点しない)。topicは期待する主題語が出力のtopicに含まれるかで判定し、表記ゆれは複数を許す
- **作り方とレビュー(オーナー合意 2026-10-24)**: Claudeが下書きし、オーナーが読んで直す。オーナーが承認した版を正式とし、以後の変更もオーナーの承認を通す(レビュー制)。初版は2026-10-24に承認した(version 1)。規模はParser 117件(つながりIntent 45・機会Intent 46・境界26)・Jev 47組(yes 22・no 25)。承認の際のオーナーの判断: お酒の有無が文面から決めにくい件(4件)はalcohol_involvedを採点しない/人数の読み方が割れる件は人数を採点しない/1件を削除/つながりIntentと機会Intentの組はLayer 1で提案されない(06 §3)ためJevの組から外す/違う地域でnoの組を4組足す
- **Parserのゴールドセットの版2(不具合の修正工程(第3回)・オーナー承認 2026-10-24・01冒頭の決定記録(不具合の修正工程(第3回))の2)**: topicに集合場所・店・駅・施設・住んでいる地域の名前を入れない規則(07 §3)に合わせて版2へ改め、topicに含まれてはいけない語`topic_none`を16件に付けた(境目のあいまいな例は`topic_none`を付けず、地名のあり・なしのどちらも正解とする。採点は07 §6)

## 4. Offline評価(品質ゲート)

07 §6の基準(form90%/topic85%/フィールド別/alcohol recall100%/Jevの順序整合)を、ゴールドセットにより測定する。**未合格のrealモード適用は禁止**(CIが防止)。四半期ごとにゲートを再実行し、悪化があればreal適用を止めて修正する。

**採点は手元・CIは記録を照合する(オーナー合意 2026-10-24・01冒頭の決定記録(LLM real接続)の3)。** 当初の「CIでゴールドセットにより自動測定する」を改める。採点は手元のコマンド`pnpm eval:gate`(`tools/eval/`・本物のParserとJevをゴールドセットで呼ぶ)で行い、合否・項目ごとの値・失敗の内訳・採点時のモデル名・指紋を記録`eval/records/gate.json`に残してリポジトリへ入れる。CIは本物のAIを呼ばない。`apps/worker/wrangler.jsonc`のどれかの環境で`LATCH_LLM_MODE=real`なら、記録があり合格であること・ゴールドセットが承認済みであること・指紋(指示文とモデル名の定数・realの呼び出し部品・期限の計算・正規化の関数・ゴールドセット2つの9ファイルのSHA-256・`tools/eval/lib/fingerprint.ts`)が今のファイルと一致すること・記録のモデル名が今の定数と同じであることを確かめ、どれかが外れればCIを落とす。照合は`tools/eval`の単体試験(Nodeのvitest・`pnpm test`に含まれる)に置く(workerの試験はminiflare上で動きリポジトリのファイルを読めないため)。指示文を1文字でも変えると指紋が変わり、採り直すまでCIが落ちる。理由: 本物のAIをCIのたびに呼ぶと費用と鍵の管理が増え、結果も揺れる。合格の記録と今のファイルの一致を確かめれば、未合格のreal適用を防ぐ目的は満たせる

**結果(2026-10-24)。** 合格(値は07 §6)。地域名をEmbedding入力に含めるかの比較(07 §4)は`pnpm eval:region`で行い、記録を`eval/records/region.json`に置いた(合否の対象ではない)

**C係数とOffline Precisionの算出定義。** C係数の再計算は、四半期ごとにcalibration_recordsからECE・Brierを算出して行い、変更はOfflineゲート通過とA/B適用を条件とする(01 §24)。Offline Precision@0.60は、ゴールドセットに手ラベルしたYES/NO正解(§3の期待値に「この2つは提案として成立し得るか」の判定を加える)に対する、閾値0.60超過提案の正解率として定義する。精度ゲートでは参考値として記録し、合否には使わない(07 §6の表に無いため・LLM real接続で確定。2026-10-24の値はTypeSafe 0.824・Anthropic 0.840)。

## 5. Online評価(A/B Test)

- 対象: 通知閾値(0.60)・通知上限(1日6件)・Candidate数(K_v)・通知文・回答期限(つながり24時間)・form確認UIの文言(表示情報量のA/Bは、visibilityの単値化(01裁定)により行わない)
- 割付: ユーザー単位・SHA-256(user_id+実験key)の偶奇。決定的
- **混在ペアは対照値を適用**(処置の混入を許さない)
- 判定不能(検出力不足)は現行値を維持する持続規定
- ベースライン: 公開後4週間の中央値を記録。**ベースライン期間中の仕様変更は凍結**(緊急修正は記録のうえ起算を延長)
