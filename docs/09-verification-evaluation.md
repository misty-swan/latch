## 2. 成功指標の測定定義

**North Star: Mutual Latch Rate。** 分母=当該期間に通知を送信した提案数(1提案1計上・グループも1提案。期限切れ・no・cancelled(競合を含む)を除かない)。分子=必要人数全員がyesした提案数。**形式別(つながり/機会)の内訳を必ず併記する。**集計はlatch_status_eventsの日次バッチ(D1)。

**主要KPI(4群・01 §23)**

| 群 | 指標 | 定義の要点 |
|---|---|---|
| 使われ方 | Intent作成率/再作成率/Active数/7日・30日継続率 | 分母=セッション開始ユーザー(sessions表) |
| マッチングの質 | Candidate生成率/提示率/保留→expired率/YES率/MLR/無回答率 | 06 §7の計測から日次集計 |
| つながりの品質 | チャット開始率(成立後7日以内に双方1件以上送信・グループは参加者全員・下記)/往復継続率(30日)/ブロック率/1つながりIntentの成立数 | messages・chat_reads・blocksから集計 |
| コスト | 1IntentあたりJev実行数/1成立あたりLLM費用 | usage_counters+費用記録 |

**Analytics諸量の集計(02 #35・F9で確定)。** 02 §4 #35の6つの数値は、D1への読み取りの問い合わせ(SELECTのみ)を送る集計のコマンド`pnpm analytics:report`(`apps/worker/scripts/analytics-report.mjs`・SQLと表の組み立ては`apps/worker/src/analytics/report.ts`)でMarkdownの表に出す。管理画面は作らない(製品の画面を増やさない)。期間は日本時間の日付で両端を含めて`--from`・`--to`で指定し(省略は直近30日)、`--now`で集計の時刻を指定できる(チャット開始の判定の境目。過去の時点の集計の再現に使う)。向け先は手元のD1(既定・`--persist-to`でE2Eの状態などを指す)とstaging(`--staging`)である。出すのは件数・割合・分布だけで、ID・本文・表示名は問い合わせの結果にも含めない(08 §6)。上の「日次バッチ」は、集計の結果を別の表に貯めず、問い合わせの中で日ごとに分けて出す形で行う(マイグレーションは無い)。問い合わせの正しさはworkerの試験(`apps/worker/tests/analytics-report.test.ts`・行を配置してD1で実行する)で確かめる。各数値の数え方は次のとおり。

| 数値 | 数え方 | 記録 |
|---|---|---|
| 候補数 | 第2段の評価1回ごとの層通過件数(Layer 2 Candidate Retrievalの取得→Layer 1の通過→Layer 3の通過→Layer 5の閾値超え→提示・保留)を、起点の意思の形式別に合計する。見出しの「候補数」はLayer 3を通ってmatch_candidatesへ保存した件数(l3_pass)で、1評価あたりの値も出す | match_eventsのpayload(06 §7)。評価した行(層通過件数を持つembedding_completed・vector_reflectionの処理済みの行)を処理した時刻で数える |
| Jev実行回数 | (1)評価の記録の呼び出し件数(1対1・グループ)と再利用件数を形式別に、(2)予算の計上を日ごとの全体と1Intentあたり(Jevを呼んだ意思1件あたり)で出す | (1)match_eventsのpayload、(2)usage_counters(jev_global_daily・jev_intent。毎分Cronの評価を含む。上限で止めた1回も試行として数える・06 §6。90日で削除) |
| LATCH Score | 件数・平均・最小・最大と0.1刻みの分布を、評価した組と提案化した組の2つで形式別に出す | 評価した組=match_candidates.latch_score(評価した期間・30日で削除・05 §2.6)。提案化した組=latches.score(作成した期間・通知上限で保留した提案を含む。グループは全ペアの最小値) |
| YES/NO | 提示した提案(proposed_atあり)の参加者ごとに、yes・no・defer・無回答を数える。YES率=yes÷参加者の延べ人数、無回答率=無回答÷参加者の延べ人数。回答期限切れで無効になったyesと本人が取り消したyesもyesに数え、その数を内訳に出す(yesと答えた反応を数えるため) | latch_members・latch_responses。提示した期間で数える |
| Mutual Latch Rate | 上の定義(分母=提示した提案・分子=成立した提案)を形式別と提示した日(日本時間)ごとに出す。成立は状態の記録にmatchedがあることで判定する(成立の後の離脱・ブロックでcancelledになった提案も成立に数える)。分母は除外をしないため、回答期間中の提案の件数を並べて出す(期間の終わりに近い日の値は回答期間が終わるまで低く出る) | latches.proposed_at・latch_status_events |
| チャット開始率 | 成立から7日以内に参加者全員が1件以上送信した成立の割合を形式別に出す。成立から7日たっていない成立は判定待ちとして分母に入れない。成立の時刻は状態の記録のmatchedの最初の時刻 | latch_status_events・latch_members・messages。成立した期間で数える |

**D1の集計に含まれない評価(オーナー決定 2026-10-26・LAT-82)。**

- 決定内容: 候補数と評価の記録のJev呼び出し件数のD1の集計には、毎分Cronが評価本体を直接呼ぶ評価((a)(b)(e)(g)(h)・06 §2)と、削除した意思の評価が含まれないことを、制約として受け入れる。評価の記録の表を新しく足すことはしない
- 根拠: 毎分Cronの評価の層通過件数はAnalytics Engineのdata pointにだけ書かれ、match_eventsのpayloadには書かれない(06 §7)。意思を削除するとmatch_eventsの行も消える(05 §2.5のプライバシーの方針)。全量はAnalytics Engine(dataset=latch_metrics・評価の起点originで経路を見分けられる)に残る。Jevの実行回数の全量は予算の計上(usage_counters)が持つ
- 影響: D1の候補数は、意思の作成・更新の直後の評価と反映確認の評価し直しだけの値になる(つながりIntentの遅延再評価(h)などの分だけ全量より少ない)。マイグレーションは無い

**グループのチャット開始(オーナー決定 2026-10-26・LAT-82)。**

- 決定内容: 3〜4人のグループLATCHのチャット開始は、成立時の参加者全員が成立から7日以内に1件以上送信したこととする(1対1の「双方」をそのまま広げる)。成立の後に離脱した参加者も参加者に数える
- 根拠: 1対1の定義と同じ考え方で数えられ、形式やグループかどうかで開始の意味が変わらない
- 影響: グループの成立は1対1より開始と判定されにくい。チャット開始率はグループを分けずに形式別に出す

## 3. ゴールドセット

- 日本語・両形式混在。規模: 各form 40件以上+境界20件以上(form曖昧・alcohol暗示表現・地域のみ添付・人数のみ添付)
- 形式: YAML(入力文・期待値の全フィールド)・リポジトリ管理・変更はレビュー制

## 4. Offline評価(品質ゲート)

07 §6の基準(form90%/topic85%/フィールド別/alcohol recall100%/Jevの順序整合/JevのRecall@0.60 80%)を、ゴールドセットにより測定する。**未合格のrealモード適用は禁止**(CIが防止)。四半期ごとにゲートを再実行し、悪化があればreal適用を止めて修正する。

**採点は手元・CIは記録を照合する(オーナー合意 2026-10-24・01冒頭の決定記録(LLM real接続)の3)。** 当初の「CIでゴールドセットにより自動測定する」を改める。採点は手元のコマンド`pnpm eval:gate`(`tools/eval/`・本物のParserとJevをゴールドセットで呼ぶ)で行い、合否・項目ごとの値・失敗の内訳・採点時のモデル名・指紋を記録`eval/records/gate.json`に残してリポジトリへ入れる。CIは本物のAIを呼ばない。`apps/worker/wrangler.jsonc`のどれかの環境で`LATCH_LLM_MODE=real`なら、記録があり合格であること・ゴールドセットが承認済みであること・指紋(指示文とモデル名の定数・realの呼び出し部品・期限の計算・正規化の関数・ゴールドセット2つの9ファイルのSHA-256・`tools/eval/lib/fingerprint.ts`)が今のファイルと一致すること・記録のモデル名が今の定数と同じであること・記録のJevのRecall@0.60(第一候補と予備)が07 §6の基準以上であること(基準を加える前の記録を通さないため・LAT-114)を確かめ、どれかが外れればCIを落とす。照合は`tools/eval`の単体試験(Nodeのvitest・`pnpm test`に含まれる)に置く(workerの試験はminiflare上で動きリポジトリのファイルを読めないため)。指示文を1文字でも変えると指紋が変わり、採り直すまでCIが落ちる。理由: 本物のAIをCIのたびに呼ぶと費用と鍵の管理が増え、結果も揺れる。合格の記録と今のファイルの一致を確かめれば、未合格のreal適用を防ぐ目的は満たせる

**結果(2026-10-24)。** 合格(値は07 §6)。地域名をEmbedding入力に含めるかの比較(07 §4)は`pnpm eval:region`で行い、記録を`eval/records/region.json`に置いた(合否の対象ではない)

**C係数とOffline Precisionの算出定義。** C係数の再計算は、四半期ごとにcalibration_recordsからECE・Brierを算出して行い、変更はOfflineゲート通過とA/B適用を条件とする(01 §24)。算出は匿名化済みの行(anonymized=true)を使い、予測値をprediction.latch_score、正解をoutcome=both_yes(成立)とする。形式・人数・時間帯の内訳はformとcontextで分けられる(行の作り方は05 §2.2・F9実装確定・LAT-108。再計算の手段(集計のコマンド)は運用データがそろった後に作る)。Offline Precision@0.60は、ゴールドセットに手ラベルしたYES/NO正解(§3の期待値に「この2つは提案として成立し得るか」の判定を加える)に対する、閾値0.60超過提案の正解率として定義する。精度ゲートでは参考値として記録し、合否には使わない(07 §6の表に無いため・LLM real接続で確定。2026-10-24の値はTypeSafe 0.824・Anthropic 0.778)。Offline Recall@0.60は、正解yesの組のうち閾値0.60を超えた組の割合(見逃しの少なさ)とする(不具合の修正工程(第6回)・LAT-109で参考値として記録を始めた。2026-10-26の値はTypeSafe 1.000・Anthropic 1.000。前の指示文の2026-10-24の記録ではTypeSafe 0.636・Anthropic 0.955)。不具合の修正工程(第7回)から、Recall@0.60は精度ゲートの合否に使う(基準80%以上・第一候補と予備のそれぞれ・オーナー決定 2026-10-26・07 §6の決定・LAT-114)。Precision@0.60とRecall@0.60は、Jevの採点に使う組(§3の`jev_scored: false`を除く)の(A,B)の順の結果で数える。否定の条件の印(07 §4)とゴールドセット版2で採り直した値(2026-10-26)は、Recall@0.60がTypeSafe 1.000(30/30)・Anthropic 1.000(30/30)、Precision@0.60がTypeSafe 0.968・Anthropic 0.968(07 §6)。
