**決定記録(2026-10-17・プロダクトオーナー)**

1. 当初構想の転職マッチング・売買マッチングは、法的な許可の負担(職業安定法の職業紹介事業許可、古物営業法・資金決済法・特定商取引法等)が大きく、製品スコープから外す
2. 製品の主軸は、ジャンルを絞らない「こういう目的で人とつながりたい」という意思(Intent)を預け、自動マッチングで相互YESのときだけつながる体験とする。X等の「#〇〇と繋がりたい」が検索とセルフアピールを要求するのに対し、本サービスは意思を置くだけでよい
3. 飲み・食事は、時間・場所を添付した「機会Intent」の第1カテゴリとする
4. 供給側Intent(店・施設が意思を預ける形)はv1.0に含めない。ただし、後から設計変更なしで追加できる拡張点をデータ設計に組み込む
5. **段階的な検証リリース(MVP・クローズドベータ等)は行わない。** 完成形(v1.0)を本書で定義し、それを作り切って公開する。リリース前には社内クローズドテスト(品質保証。検証装置ではない)を実施する
6. 提供形態は**PWA(スマホ画面対応のWebアプリ)**とする。ネイティブアプリ(iOS/Android)は利用定着後の拡張とし、着手基準は後続文書で定める
7. プロダクト名はLATCHに確定した(2026-10-17)。改名候補8件の同名調査の結果、日本のSNS・マッチング領域への衝突なしとして継続した。正式な商標調査(J-PlatPat)は開発着手前の確認事項とする
8. 実装は本リポジトリで最初から構築する(技術スタックは04が選定する)

**決定記録(2026-10-20・プロダクトオーナー)**

1. 未提示・システムの都合で閉じた提案は提案履歴を消費しない
   - 決定内容: 一度も提示しないまま閉じた保留(保留中の期限切れ・機会の対象時刻まで75分を切ったもの・参加Intentの終了)と、システムの都合で閉じた提案(機会の排他・Intent削除・条件変更=Hard Constraintの変化)は、提案履歴(proposal_history)を消費しない。そのLATCHのために新規に確保した行は削除し(ペアは未提案に戻る)、再提案で確保した既存行はexpiredに戻す。提示後に回答期限が切れた提案・見送り(defer)・明示の拒否(no)は従来どおりexpired / deferred / rejectedを記録する
   - 根拠: 恒久排除は「成立・明示の拒否(no)」のみとする裁定(第8節・2026-10-17)の趣旨は、利用者自身の行動による排除に限ることにある。本人が見ていない・選んでいない提案で組み合わせが失われるのはこの趣旨に反する
   - 影響: 第8節の「つながりIntentはいずれの履歴でも再提案は1回きり」は提示された提案についての規則となる。第17節・第21節の提案履歴の保持は「成立・拒否・見送り・提示後の期限切れの履歴は保持し、進行中の提案のために確保した行は解放する」に揃える(05 §2.2・§2.5・§3.2、06 §4)
2. 意味フィールドの更新で30分の再評価抑制を解除する
   - 決定内容: active Intentの更新で意味フィールド(topic・time・geo・participants・budget・constraints)が変わったとき、同一Intent再評価の30分頻度制限(第16節)を解除する(並行更新で版が進んでいれば解除しない)。表示系(notification_level等)だけの変更では解除しない
   - 根拠: 30分の頻度制限は同じ内容の繰り返し評価を防ぐためのもので、内容が変われば理由がない。条件変更で進行中の提案が取り消された直後に、新しい条件での再提案が最大30分遅れるのを防ぐ。費用は更新6回/時(04 §5)とJev予算(1Intentあたり1日40回)で別に抑えられている
   - 影響: 第16節の30分頻度制限に「意味フィールドの更新は除く」を添える(05 §2.2・§3.2、06 §3・§6)
3. 地域名をEmbedding入力に含めるかは「Parser/Jevのreal接続と精度ゲート」の工程で扱う
   - 決定内容: 07 §4の「地域名を入力に含めるかはF4で再検討」を、12のLLM real接続(F9前の独立工程)で扱うと改める
   - 根拠: stubのEmbeddingでは効果を測れず、realのEmbeddingとゴールドセットでの比較が必要である。入力テキストは将来のJev外部送信(第21節)に乗るため、08の外部送信の判断と同じ場で決める
   - 影響: 07 §4の文言と12 §2の工程表のLLM real接続の行を改める(08は参照のみで内容の変更はない)

**決定記録(2026-10-20・プロダクトオーナー・グループLATCH)**

1. グループ提案がdefer / noで閉じたときは、閉じた本人を含むペアだけを提案履歴に記録する
   - 決定内容: グループ提案(3〜4人)が見送り(defer)または明示の拒否(no)で閉じたとき、提案履歴(proposal_history)は閉じた本人を含むペアだけを記録する(defer=deferred・no=rejected)。本人を含まないペアは履歴を消費しない(そのLATCHのために新規に確保した行は削除し、再提案で確保した既存行はexpiredに戻す。直前の決定記録(2026-10-20)の1の「消費しない」と同じ扱い)
   - 根拠: 本人以外の組は意思表示をしていない。つながりIntentは既存の履歴行があれば再提案しないため、全ペアを記録すると本人以外の参加者どうしが以後1対1でも出会えなくなる
   - 影響: 第15節にグループの履歴の記録範囲を添える(05 §2.2、06 §4)。1対1では唯一のペアが常に本人を含むため、挙動は変わらない
2. グループ提案が回答期限切れで閉じたときは、有効なyesを持たない参加者を含むペアだけをexpiredで記録する
   - 決定内容: グループ提案が回答期限までに必要人数のYESに届かず閉じたとき(expired)、有効なyesを持たない参加者を含むペアだけをoutcome=expiredで記録する。yesどうしのペアは履歴を消費しない(決定1と同じ扱い)
   - 根拠: 決定1と同じ考え方である。互いにyesだった組は相手を拒んでいない
   - 影響: 06 §4のグループ期限切れの履歴の規定(全ペアを記録する旨)を本決定の規則に改める(05 §2.2)。1対1では期限切れのペアは必ず非yesの参加者を含む(双方yesなら成立済み)ため、挙動は変わらない
3. 成立後の参加取り消し(leave)は、抜けた本人だけをLATCHから外し、残りが必要人数の下限を割ったときにLATCH全体をcancelledとする
   - 決定内容: 成立後のleaveは本人の離脱だけを記録してLATCHをmatchedのまま続ける。離脱後の残りの参加者数が提案内容の人数の下限(proposal.participants.min)を割る場合はLATCH全体をcancelledとする(成立後の離脱のため不成立の通知は作らない)。離脱者の提案履歴はmatchedのまま変えない
   - 根拠: 05 §3.3の既定どおりである。1対1は1人抜けると下限2を割るため、従来と同じ挙動(LATCH全体のcancelled)になる
   - 影響: 05 §2.2のlatch_membersに離脱時刻(left_at)を加え、離脱者からは当該LATCHを非参加と同じに扱う(05 §3.3)。第15節に離脱の規則を添える

**決定記録(2026-10-21・プロダクトオーナー・つながりの性質)**

1. 機会LATCHのcompleted判定をF5で扱い、LATCHの自分の側の削除とフィードバック申告の工程を割り当てる
   - 決定内容: 機会LATCHのcompleted判定を、つながりLATCHの90日判定と同じ毎分Cronの走査(06 §2の(d))で実装する。`DELETE /v1/latches/{id}`(自分の側の表示削除・02 D-08)はF6、`POST /v1/latches/{id}/feedback`(第14節の自己申告)はF9で実装する(12 §2)
   - 根拠: completedへの遷移を1か所にそろえ、F6のチャットの読み取り専用化の前提を整える。削除は成立一覧とチャットの画面と、自己申告は正解データの集計(02 #35)と同じ工程で扱う方が設計と検証の単位がまとまる
   - 影響: 06 §2の(d)を機会LATCHまで広げる(04 §4・05 §2.6)。12 §2のF6・F9の内容に担当を追記する
2. 機会LATCHは対象時刻から3時間の経過でcompletedとする
   - 決定内容: 第8節の「機会Intent由来のLATCHは対象時刻の経過でcompleted」の境界を、対象時刻(提案内容のtime_window.start。グループは全員のstarts_atの最大値)から3時間の経過と定める
   - 根拠: 対象時刻ちょうどで閉じると、F6でチャットが読み取り専用になったとき、当日の連絡が最も必要な時刻にチャットが閉じる。3時間は機会Intentの既定の期限(start+3時間・05 §2.2)と同じ幅である
   - 影響: 第8節と主要値の一覧に境界を添える(05 §2.2・§2.6、06 §2)

**決定記録(2026-10-21・プロダクトオーナー・チャット)**

1. 続いているLATCHを表示から消すと、本人はそのLATCHから抜けたものとして扱う
   - 決定内容: matched(続いている)のLATCHを自分の側の表示から消す操作(`DELETE /v1/latches/{id}`・02 D-08)は、参加取り消し(leave)と同じ処理に表示削除の印を加えたものとする。1対1はLATCH全体がcancelledとなり、相手の側は「このつながりは終了しました」と読み取り専用の履歴になる。グループは本人だけが抜け、残りが必要人数の下限を割ったときにLATCH全体がcancelledとなる(2026-10-20の決定記録(グループLATCH)の3と同じ規則)。completed・matched経由のcancelledのLATCHを消したときは本人の表示から隠すだけで、相手の側の表示・人数は変えない
   - 根拠: 消した本人に見えないメッセージが相手から届き続ける状態を作らない。相手の側に終了の理由を区別して見せない原則(第10節)にも合う。D-08の「相手側の表示は残る」は履歴の表示として守られる
   - 影響: 第8節・第10節・主要値の一覧の削除の規定に添える(02 D-08)。05 §2.2のlatch_membersに表示削除の時刻(hidden_at)を加え、消した本人からは当該LATCHを非参加と同じに扱う(05 §3.3)。工程(F6のF6a・F6bへの分割)の決定は12 §2に置く
2. 離脱でLATCH全体が終わるとき、離脱した本人も読み取り専用の参加者として残る
   - 決定内容: 参加取り消し(leave)でLATCH全体がcancelledになるとき(1対1は常に。グループは残りが必要人数の下限を割ったとき)、離脱した本人も取り消し済みLATCHの参加者として残る。本人は成立一覧で終了したLATCHを見られ、履歴を読め、既読を記録できるが、送信とチャット接続はできない(双方読み取り専用)。残った側に見える参加者・人数にも本人は残る。本人が見えなくしたいときは表示から消す(DELETE)。LATCHが続くグループからの離脱者は従来どおり抜けた本人として扱い、当該LATCHを見られない
   - 根拠: 第10節の「参加取り消し(leave)は1対1はチャットを双方読み取り専用にする」と`prototype/`の「チャットはお互いに読み取り専用になります」に合わせる。実装中に置いた暫定の扱い(全体を取り消した本人も抜けた本人として見えなくする)はこの判断で撤回した
   - 影響: 05 §2.2のlatch_membersのleft_atを、全体を取り消す離脱では記録しない(05 §3.3の一覧・離脱・DELETEの規定)。工程の要点は12 §2の決定記録に置く

**決定記録(2026-10-21・プロダクトオーナー・チャットの画面)**

1. 「表示から消す」の説明文を、LATCHの状態で分ける
   - 決定内容: 続いている(matched)LATCHの「表示から消す」の説明文は「このつながりを終えて、自分の一覧から消します。相手の側には履歴が残ります。」とする(グループは「このつながりから抜けて、自分の一覧から消します。相手の側には履歴が残ります。」)。終了後(completed・成立後のcancelled)は「自分の一覧から消します。相手の側には残ります。」とする
   - 根拠: 続いているLATCHの削除は離脱を伴い(上記のチャットの決定記録の1)、終了後の削除は相手の側を変えない。同じ「表示から消す」でも結果が違うため、押す前に利用者へ違いが伝わる文言にする
   - 影響: 第10節の一覧の操作ラベルに反映する。グループの「参加を取り消す」の説明文「このつながりから抜けます。」は文書の裁量で定めた(`prototype/`は1対1のみ)
2. 「参加を取り消す」「表示から消す」の前に確認を一段挟む
   - 決定内容: 操作メニューで「参加を取り消す」「表示から消す」を選ぶと、同じシートの中で「元には戻せません。」の確認([取り消す]・[消す]/[やめる])に切り替え、確認の後に実行する
   - 根拠: どちらも元に戻せない操作で、押し間違いの損失が大きい。`prototype/`の操作メニューには確認の段が無かった
   - 影響: 画面だけの変更で、APIの変更は無い(05 §3.3)
3. 1通の上限はAPIの2,000字に揃える
   - 決定内容: チャットの入力欄の1通の上限は、APIの2,000字(05 §2.2・前後の空白を除く)とする
   - 根拠: `prototype/`の入力欄は1,000字だが、データモデルとAPIの規定が2,000字で確定している。画面だけが厳しいと、同じ本文がRESTでは通るのに画面では送れない食い違いになる
   - 影響: `prototype/README.md` §7の確認事項に追記する。試作品のボードは更新しない

**決定記録(2026-10-21・プロダクトオーナー・安全のAPI)**

1. 1対1のつながりでのブロックは、ブロックした本人の参加取り消しと同じ処理でLATCH全体を終える
   - 決定内容: 続いている(matched)1対1のLATCHで相手をブロックすると、ブロックした本人について参加取り消し(leave)と同じ処理を行い、LATCH全体をcancelledにする。双方とも読み取り専用の履歴が残り(上記のチャットの決定記録の2)、ブロックされた側には参加取り消しと区別できない「このつながりは終了しました」だけが見える。08 §8の「ブロックされた側は当該LATCHのメッセージを取得できない(NOT_FOUND)」は撤回する
   - 根拠: 第10節の「相手の参加取り消し・ブロック・退会のいずれであっても、残された側には理由を開示せず読み取り専用の履歴のみを表示する」に揃える。NOT_FOUNDにすると一覧から消えることで、参加取り消しとブロックの違いが相手に分かる
   - 影響: 08 §8のブロックの規定を書き換える。05 §3.3のブロックのAPIに即時効果の順序(進行中の提案の取り消し→続いているLATCHからの本人の離脱)を記す。ブロックされた側へのアプリ内通知は作らない
2. グループLATCHでのブロックは、ブロックした本人がそのLATCHから抜ける
   - 決定内容: 続いている(matched)グループLATCHでメンバーの1人をブロックしたときは、ブロックした本人が参加取り消し(leave)と同じ処理でそのLATCHから抜ける(残りが必要人数の下限を割ればLATCH全体がcancelled。2026-10-20の決定記録(グループLATCH)の3と同じ規則)。ブロックされた人を外すことはしない
   - 根拠: ブロックされた人にも他のメンバーにも「1人が抜けた」としか分からない。1対1の扱い(本記録の1)と同じく、ブロックした本人が自分の参加を終える考え方で揃える
   - 影響: 08 §8・05 §3.3に添える。成立前の進行中の提案は、1対1・グループとも提案全体を閉じる(05 §3.3)
3. 提案段階の通報は、自分以外の全参加者を対象者として記録する
   - 決定内容: 成立前の提案の通報(「この提案を通報する」・08 §8)は、自分以外の全参加者を通報の対象者として1人1行で記録する。通報しても提案は閉じない(回答は別に行う)。対象者には通知しない
   - 根拠: 成立前は相手が見えないため、本人に対象者を選ばせられない。対象者ごとの行にしておくと、同一対象への重複通報の統合(08 §8)を運用で行える
   - 影響: 05 §2.2のreportsに通報の対象の種別(target)と対象メッセージ(message_id)を加える(マイグレーション0006と戻す手順・12 §4)。08 §8に提案段階の対象者と通報者内の統合を添える。工程(F7のF7a・F7b・F7cへの分割)の決定は12 §2に置く
4. 成立後の参加者だった人は、ブロックや参加取り消しで抜けた後も通報できる
   - 決定内容: 成立後の通報(プロフィール・アイコン・メッセージ)は、そのLATCHの成立後の参加者だった人なら、ブロック(本記録の2)や参加取り消しでLATCHから抜けた後(left_atあり)でも受け付ける。対象者がそのLATCHのメンバーであること、メッセージは対象者の発言であることの確認は変えない。提案段階の通報(本記録の3)は変えない
   - 根拠: グループでのブロックは本人の離脱を伴うため、抜けた人を通報できないとすると「ブロックしてから通報する」という自然な流れで通報できなくなる。安全機能が操作の順番に左右されないようにし、08 §8の「提案・成立の各状態から通報できる」に合わせる
   - 影響: 05 §3.3の成立後の通報の条件を「自分が成立後の参加者だった(left_at・hidden_atは問わない)」に改める。抜けた人は履歴を新たに読めないため、抜けた後の画面で選べる対象(メッセージを含めるか)はF7c(画面)の設計で決める

**決定記録(2026-10-21・プロダクトオーナー・通知のAPI)**

1. notification_level=mutedはWeb Pushだけを止め、アプリ内通知は作る
   - 決定内容: Intentのnotification_level=mutedは、そのIntentが参加するLATCHの提案(proposed)と成立(matched)のWeb Pushをどちらも送らない。アプリ内通知はmutedでも作る。1日6件の通知上限(第10節)の数え方は変えない(mutedの提案も1件として数える)
   - 根拠: 「この意思ではスマホを鳴らさない」という意味に揃える。アプリ内通知に残るため、提案と回答期限を見落としにくい。通知上限の数え方を変えないため、mutedへの切り替えで提案の流量が増えることもない
   - 影響: 第10節の通知の経路と種別・主要値の一覧のnotification_levelに添える。05 §2.2のnotificationsに送信の状態(push_state=muted)を記録する。Web Pushを書き込みの直後に同じWorker内で送り、送れていない行を毎分Cronで回収する構成(同日のオーナー裁定)は04 §3.4・§4に、工程の記録は12 §2に置く

**決定記録(2026-10-21・プロダクトオーナー・安全と通知の画面)**

1. 利用規約・プライバシーポリシーは、草案をF7cで書いて画面に置き、法務確認はオーナーが後で行う
   - 決定内容: 利用規約・プライバシーポリシーの草案をF7cで書き、サインイン前から開けるページ(`/terms`・`/privacy`)に置く。草案には08 §10の必須事項(規制領域の禁止・外部送信の明示・未成年条項・退会後のメッセージの保持・バックアップ7日の保持・ユーザーアイコンの権利義務・地名データのクレジット等)を含め、冒頭に「この文書は法務確認前の草案です。」の印を付ける。法務確認(02 #31の証明)はオーナー(人間領域)が後で行う
   - 根拠: 法務確認には確認の対象となる文書が先に要る。枠だけ作って文面を後で差し込む案・F10へ回す案では、法務確認を始められない
   - 影響: 08 §10に草案の置き場所を、11 §1のチェックリストに草案の配置済みと法務確認の未了を記す。02 #31は草案の配置までがF7cで、法務確認の記録は未了のまま残る(12 §2)
2. 発言の通報はチャットの相手の発言から始め、発言と相手を自動で決める
   - 決定内容: 成立後の発言(target=message)の通報は、チャットの相手の発言の操作(長押し・発言横のメニュー)の「このメッセージを通報する」から始め、通報する発言と相手(発言者)を自動で決める(通報画面は理由と補足だけを選ぶ)。自分の発言には出さない。チャットの操作メニュー(「…」)からの通報はプロフィール・アイコンのどちらかを選ばせ、グループでは相手(自分以外の参加者)を選ぶ欄を加える
   - 根拠: 通報画面で相手の発言の一覧から選ばせる案は操作が増え、直近の発言を自動で対象にする案は誤った発言を記録し得る。発言そのものから始めれば、対象を取り違えない
   - 影響: 08 §8の通報の導線に添える。APIの変更は無い(05 §3.3)。上記の安全のAPIの決定記録の4で画面の設計に残した「抜けた後に選べる対象」は、通報の入口をチャット(と提案画面)に置くことで定まる: 1対1でブロックした本人は読み取り専用のチャットから引き続き通報でき、続いているグループから抜けた本人はそのLATCHを開けないため、抜けた後の通報の入口は設けない
3. グループのチャットにも「ブロックする」を置く
   - 決定内容: チャットの操作メニューの「ブロックする」をグループにも置く(`prototype/`は1対1のみ)。グループでは先にブロックする相手を選び、確認のシートでブロックの結果を伝えてから実行する
   - 根拠: グループでブロックを置かないと、抜けても同じ相手との提案が届き得る。ブロックの効果(上記の安全のAPIの決定記録の2)をグループでも使えるようにする
   - 影響: 08 §8のブロックの導線に添える。確認のシートの説明文は文書の裁量で次のとおり定めた(`prototype/`の1対1の文言「このつながりのチャットは、読み取り専用になります。」を基にする): 続いている(matched)グループでは1項目目を「このグループから抜けます。」とし、「チャットは読み取り専用になります。」は添えない(ブロックした本人は抜けて、下限を割らずに続くグループは以後読めなくなるため)。終了後(completed・成立後のcancelled)のグループでは1項目目を出さない(ブロックは終了したLATCHを変えないため・08 §8)。2項目目以降(「今後、この相手との提案は届きません。」「ブロックしたことは、相手に通知されません。」)は1対1と同じとする

## 第I部 なぜこのサービスを作るのか

### 1. コンセプト — 探し、アピールする代わりに、Intentを置いて待つ

「イラストを描く人と繋がりたい」。この意思を持った人が、今のサービスでやることは、ハッシュタグを検索し、アカウントを眺め、誰かをフォローし、反応を待つことだ。あるいはコミュニティに飛び込み、自己紹介を書き、様子を見る。本サービスはこの動線を前提としない。ユーザーは条件付きの意思(Intent)を預けて、あとは待つ。

```text
Intentを置く → 待つ → 条件一致 → 提案 → 双方承認 → つながり
```

留意しておきたいのは、このサービスが扱うのが人そのものの相性ではないことだ。特定の目的・主題・条件・文脈において、2つの意思がつながりとして成立し得るかどうかである。

### 2. 解決する問題 — 「繋がりたい」の中間帯を拾うコストが高すぎる

対象となる意思には共通の形がある。積極的なYESではないが、条件が合えばYESになる、という中間帯だ。

> コミュニティを探すほどではない。でも同じことをやっている人がいるなら繋がりたい。
> わざわざ募集するほどではない。3人集まるなら始めたい。

既存サービスはこの中間帯を拾えない。拾おうとすると、ユーザー自身が動くしかない。検索し、相手に当たりをつけ、投稿し、反応を待ち、うまくいかなければ再検索する。これらはすべて目的ではなくコストであり、断られるかもしれない心理コストとセットになっている。目的は繋がることのほうにある。

本サービスはこの探索コストと拒絶コストを可能な限りゼロに近づける。「条件が合えば繋がりたい」という意思だけを預けておけば、双方がYESになり得る相手が現れた瞬間にだけ、提案が来る。拒絶はUI上存在しない。不成立の通知は「この提案は成立しませんでした」の一文だけだからである。

X等の「#〇〇と繋がりたい」との違いを明確にしておく。あちらは、(i)自分でハッシュタグを検索する、(ii)自分からアピールする(呟く・フォローする)、(iii)つながりが一方向(フォロー)である、という3つのコストと性質を持つ。本サービスは、(i)意思を置くだけ、(ii)相互YESのときだけ提案される、(iii)つながりは常に双方向である。この3点が差のすべてであり、「探索コストの除去」という効用定義を、ジャンルを問わずそのまま主張できる。

### 3. 対象ユーザー

主要な対象は「積極的に探すほどではないが、条件が合えば繋がりたい」ユーザーである。典型は次のような心理だ。

- 新しく何かを始めたい(趣味・学び・運動)。ただし、コミュニティを探して飛び込む勇気までは要らない
- 同じ状況にいる人と軽く繋がりたい(子育て・移住・介護・転勤・フリーランス)
- 既存SNSで「繋がりたい」と呟いても埋もれてしまう
- 地方や不規則な生活で、職場・地域・サークルといった既存の接点が機能していない

### 4. 製品の前提 — リリース後に計測で確かめること

この製品は次の6つの前提の上に成り立つ。段階的な検証リリースは行わないため、これらは「出荷前のゲート」ではなく、**リリース後に成功指標(第23節)で健全性を確認する前提**である。前提が崩れた場合は、運用中の改善(再設計を含む)で対応する。

1. ユーザーは「探す・アピールする」より、Intentだけ登録して待つ体験を便利と感じる
2. 完全一致ではなくても、意味的に成立する提案を受け入れる
3. 双方YESの予測は、Hard Constraint + Semantic Retrieval + Jev(第13節)で一定精度まで実現できる
4. 提案通知の頻度を抑えれば、通常のSNS通知より高い反応率を得られる
5. 「検索しない・募集しない」という行動様式自体が継続利用につながる
6. **密度前提**: 時間・地理の添付を持たないIntentは、ユーザーが地理的に分散していても、提案・成立が発生する密度で運用できる

前提6は本書の要である。地域密着型のマッチングが初期に直面する最大の運用リスクは、初期密度要件(単一エリアへのIntent集中)である。時間・地理を持たないつながりIntentは全国を1つのプールとして扱えるため、この制約を撤去できる。

## 第II部 扱うものとスコープ

### 5. 基本用語

**Intent**は、ユーザーが預ける「条件付きの意思」を指す。Intentは必ず次の2形式のいずれかに属する。

- **つながりIntent(form=connection)**: 時間・場所を添付しない。「繋がりたい」関係の形成そのものを目的とする。寿命は週〜月単位。地域のみを添付できる(「鹿児島でサイクリングする人と」というように、活動域を限定した関係)
- **機会Intent(form=occasion)**: 開始時刻を添付する。「今夜20時から飲みたい」のような、特定の機会の成立を目的とする。寿命は時間〜日単位である

**添付(Attachment)**は、時間・地域・人数・予算のうち、ユーザーがIntentに任意に付けた条件を指す。付けたものはHard Constraintとして扱う。機会Intentでは開始時刻の添付が必須(機会の定義そのもののため)。つながりIntentでは開始時刻を持てず、地域・人数・予算のみ添付できる。

その条件は2種類に分ける。絶対に満たすべきものを**Hard Constraint**と呼び、原則としてAIに判定させず、コードとDBで厳密に落とす。多少のズレを許容できる意味的・文脈的な条件を**Soft Constraint**と呼び、EmbeddingやLLMで意味的に評価する。「初心者でも歓迎してほしい」「雑に楽しくやれる相手がいい」のような条件が典型である。NG条件は判定データの有無で所属が分ける規則も同じである(システムが判定できるものはHard、判定データを欠くものはSoft側へ降格して注意表示)。

一次候補検索(Layer 2 Candidate Retrieval)の取り出し幅から得られ、詳細判定に回るIntentを**Candidate**と呼ぶ。CandidateのうちIntentペア単位のものを**MatchCandidate**と呼ぶ。ユーザーへ提示された候補を**LATCH候補**(提案)と呼ぶ。2つ以上のIntentについて、双方または参加者全員の条件が一定水準以上で成立し、必要人数全員がYESした状態を**LATCH**と呼ぶ。LATCH成立時に解放されるチャットと、その後に続く関係を**つながり(connection)**と呼ぶ。つながりは、LATCHデータ上はmatched状態のレコードとして表現される。

Intent同士が実際につながる可能性を内部的に表すスコアが**LATCH Score**である(算出方法は第13節)。恒久的な人間の相性ではなく、その目的・時点・文脈における意思の成立可能性を示す。

**Event**は、再評価を発生させる状態変化を指す。発生するのは、Intentの作成・更新・削除・期限切れ、指定時刻の到来(機会Intentのみ)、Embedding完了の派生イベントである。つながりIntentは時間Bucketを持たないため、「指定時刻の到来」の対象外である(第11節・第16節)。

**画面コピーの用語対照。** ユーザーに見せる語は次の対照に従う(システム語→表示語)。Intent→「預けた意思」(「Intent」という語は画面に出さない)/ form=connection→「つながり」/ form=occasion→「機会」/ LATCH候補・提案→「提案」/ LATCH成立→「つながる」。サービス名LATCHはサービス自身を指す場合にのみ使う。

### 6. ユースケース — ジャンルを問わないつながりと、機会の第1カテゴリ

v1.0が扱うのは、**ジャンルを問わないつながりIntent**と、**機会Intentの第1カテゴリ(飲み・食事・軽いアクティビティ)**である。

つながりIntentの例:

```text
個人開発をやっている人と繋がりたい。
子育て中の親と、気軽に話せる繋がりが欲しい。
英語を母語とする人とランゲージエクスチェンジしたい。
鹿児島でサイクリングする人と繋がりたい。(地域添付)
イラストを描く人と、月1で雑に絵を見せ合える関係になれたら嬉しい。
```

機会Intentの例(第1カテゴリ):

```text
今日20時以降、天文館周辺で、2〜4人、予算5,000円以内なら軽く飲みに行きたい。
```

この構成の理由は次のとおりである。つながりIntentがコンセプトの本体であり、前提6(分散密度)を支える形式である。機会Intentは「時間・場所の添付がHard Constraintとして明確に機能する」「短いサイクルで正解データが取れる」形式である。よって機会Intentを第1カテゴリとし、両形式が同じパイプラインを流れる構造にする。

スコープから外す領域と理由:

| 領域 | 扱い | 理由 |
|---|---|---|
| 転職マッチング | 行わない(規約で禁止) | 職業安定法。職業紹介事業は有料・無料を問わず厚生労働大臣の許可制であり、「システムが能動的に双方を結びつけて提案する」方式は紹介事業に該当しやすい |
| 売買マッチング(中古品等) | 行わない(規約で禁止) | 古物営業法(公安委員会の許可)・資金決済法(資金を預かる立場)・特定商取引法と、規制が重層する |
| 異性交際を目的とする使用 | 行わない(規約で禁止) | 出会い系サイト規制法に該当しない設計を維持するため(第22節) |
| 供給側Intent(店・施設) | v1.0に含めない。**データ設計に拡張点のみ確保**(第17節) | 個人同士のつながり意思の集積(需要の見える化)を先に作る。追加はactor拡張と条件タイプ追加で行い、既存テーブルの破壊的変更を不要にする |

これらの法令解釈の最終確認は、リリース前に弁護士等の法務確認を前提とする。本書の記述は一般論としての判断である。

## 第III部 ユーザー体験

### 8. ユーザーフロー

つながりIntentの基本フローは次のとおりである。

```text
自然言語でIntent入力
  ↓ Intent Parserで構造化(form=connectionと判定)
  ↓ ユーザーが確認・修正
  ↓ Intent保存(長寿命) → Match Event発火
  ↓ 待機(週単位。待つことが正常な状態)
他のユーザーが意味的に近いIntentを登録
  ↓ 評価 → LATCH Scoreが閾値超過 → 提案
  ↓ ユーザーA: YES
  ↓ ユーザーB: YES
LATCH成立 → チャット解放(つながり確立) → Intentはactiveへ復帰
```

機会Intentのフローは短寿命・回答期限式・競合による排他である。

**成立の定義。** 必要人数全員のYESでLATCHが成立(matched)し、チャット・表示名・プロフィールが解放される。つながりIntent由来のLATCHは対象時刻を持たないため、matchedのまま維持し、**チャットの非活動期間が90日を超えた時点でcompleted**とする(つながりの静穏。アーカイブ導線の詳細は`prototype/`基準で実装する)。機会Intent由来のLATCHは対象時刻から3時間の経過でcompletedとする(2026-10-21オーナー裁定・冒頭の決定記録)。completed後もチャット履歴は読み取り専用で閲覧でき、ユーザーは自分の側からLATCHを削除できる(D-08。相手側の表示は残る)。続いている(matched)LATCHの削除は本人の離脱を伴う(2026-10-21オーナー裁定・冒頭の決定記録)。

**つながりIntentの複数成立。** つながりIntentは、LATCH成立後もIntentをactiveへ復帰し、複数のつながりを形成できる。関係形成が「1回きりの消費」でないためである。機会Intentは排他(1つのIntentが同時に複数の成立済みLATCHに属さない。「他のLATCH成立による競合」の閉じ経路は機会Intentのみに適用)。

**同一ペアへの再提案排除(2026-10-17オーナー裁定)。** 提案履歴(proposal_history)はユーザーペア単位で保持する。**成立(matched)と明示の拒否(no)の履歴があるペアは、以後一切候補化しない(恒久排除)。** 見送り(defer)・回答期限切れ(expired)の履歴は排除の対象とせず、機会Intentに限り、見送り後 min(24時間, 対象時刻までの残時間の半分) の抑制期間を経て、スコア変化またはどちらかのIntent更新を条件に再提案する。つながりIntentは状態が変わらないため、いずれの履歴でも再提案は1回きりである(見送り後の再提案は行わない)。この「1回きり」は提示された提案についての規則である。**一度も提示しないまま閉じた提案(保留中の期限切れ・参加Intentの終了)と、システムの都合で閉じた提案(機会の排他・Intent削除・Hard Constraintの変化)は提案履歴を消費しない**(そのLATCHのために新規に確保した履歴は解放してペアを未提案に戻し、再提案で確保した既存の履歴は期限切れに戻す。2026-10-20オーナー裁定・冒頭の決定記録)。

**不成立経路。** 提案は次のいずれかで閉じる(形式別に整理)。片方がNOと回答した / 回答期限が切れた / Intent期限が切れた / Hard Constraintが変化した / 必要人数が揃わなかった / ブロックに該当した / (機会Intentのみ)他のLATCH成立による競合が起きた / 参加Intentが削除された。

**回答期限。** 機会Intentの導出規則は min( max(通知+15分, min(通知+2時間, 対象時刻−60分)), 参加Intent期限の最小値 ) とする(対象時刻=機会Intentのstarts_at)。つながりIntentは対象開始時刻を持たないため、**min(通知時刻+24時間, 参加Intentのexpires_atの最小値)**とする。24時間は、長寿命の意思に対して落ち着いて回答できる余裕としての値である。

### 9. Intent入力 — 自然言語を構造化して確認する

入力は自然言語を基本とする。フォーム入力を主UIにはしない。

```text
イラストを描く人と繋がりたい。初心者だけど、
月に1回くらい雑に絵を見せ合える相手がいると嬉しい。
```

Intent Parserはこの文章から最低限、次のフィールドを抽出する。

```yaml
intent_id:
user_id:

form: connection / occasion   # Parserが判定。確認画面でユーザーが切替可能

topic: イラスト仲間           # 必須。主題の短句
category:                     # 任意。流量制御用の低粒度タグ(初期セットは未決D-03)

time:                         # つながりIntentではnull。機会Intentはstart必須
location:                     # 任意添付。中心と半径(つながりIntentでは「活動地域」)
participants:                 # 任意。既定 min=2 / max=2
budget:                       # 任意。機会Intent中心

visibility: hidden_until_match   # 単値(v1.0の値はこれのみ。02のQ2裁定)
notification_level: proposals_only   # proposals_only / muted の2値(近い候補通知は持たない)

expires_at:                   # つながりIntent: 選択式 7/30/90日・既定30日
                              # 機会Intent:   既定 time.start+3時間

raw_text:                     # 最大300字
alcohol_involved:             # 機会Intentの飲酒判定

hard_constraints: []
soft_constraints: []
negative_constraints: []
```

必須フィールドは**topic(主題)とformのみ**である(時刻・場所・カテゴリを入力必須としないことが、本設計の骨格である)。時間・場所・人数・予算はすべて任意添付になり、未指定の添付は制約なしとして扱う。

構造化した内容は、保存前に必ずユーザーへ見せる。修正もできる。確認画面にはformの判定を含め、**「つながりとして預ける(すぐに会う予定はない)」「機会として預ける(日時がある)」**として示す。読み取りの典型ミスはformの取り違れである(「今度飲みに行く仲間が欲しい」は関係の要求であり機会の要求ではない)。この確認を第2画面(読み解き確認)の責務とする。

```text
LATCHは以下の条件として理解しました。

形式: つながりを探す
主題: イラスト仲間
条件: 初心者歓迎 / 月1回程度 / お互いの絵を見せ合う
期限: 30日間
```

曖昧表現の丸め規則、Parser失敗時の構造化フォームへのフォールバック、下書き保存(raw_textのみで保存し検証とEvent発行はactive化まで行わない)を適用する。飲酒の関与(alcohol_involved)の判定と20歳未満作成不可の検証も、機会Intentに限り適用する。

### 10. 通知と画面

LATCH Scoreが設定閾値(初期値0.60)を超えたら通知する。通知はWeb Push通知(本文は汎用文)とアプリ内通知(お知らせ)の併用、回答は提案画面の2択([参加する][今回は見送る])からのみ、という規定を両形式に適用する。**回答値の対応は yes=[参加する] / defer=[今回は見送る] の2つがUIの2択であり、no(明示の拒否)はUIに置かずAPI契約(05)のみで受け付ける。**

通知頻度の上限は1ユーザーあたり日6件・1Intentあたり同時進行3件とし、超過分は保留する。保留キューの提示順序は、機会Intentは対象時刻の近い順、**つながりIntentはLATCH Scoreの高い順**とする(対象時刻がないため)。提示時に回答期限を再計算する。

画面は5画面フロー(01預ける → 02読み解き確認 → 03待機中 → 04候補が届く → 05成立・チャット)+簡易一覧2画面を基本構成とする。これに加え、初回登録・外部送信の同意・プロフィール/設定(通知・ブロック管理・退会を含む)・下書きを含むIntent一覧・成立一覧・通報の画面が最低限必要である(画面インベントリの全体は`prototype/`が示す)。実装基準は`prototype/`。つながりIntentの「待機中」は週単位の滞留が正常になるため、待機中のカードには経過日数・期限・これまでの成立数を表示する。

状態は2系統ある(形式別の調整を含む)。

```text
Intent: draft / active / paused / matched / expired / cancelled
LATCH:  candidate / proposed / partial_accept / matched / rejected /
        expired / cancelled / completed
```

Intentは、つながりIntentではLATCH成立後にactiveへ復帰する(第8節)。機会Intentは成立でmatchedのまま。pausedは一時停止、cancelledは打ち切り、expires_at経過でexpired。LATCH側の状態で、つながりIntent由来のmatchedは「つながり確立」を、completedは「つながりの静穏」を意味する。

見送り理由(任意)の収集、回答取り消し・参加取り消し、不成立時の開示が「この提案は成立しませんでした」の一文のみであることも本規定とする。

**通知の経路と種別。** Web Pushで送るのは提案(proposed)と成立(matched)の2種のみとし、不成立(closed)・Intentの期限切れはアプリ内通知のみとする。matched通知の本文も成立前の条件を含まない汎用文とする。Web Pushの購読依頼は初回Intent保存後に行い、許可がない場合はアプリ内通知で代替できる旨を待機中画面に表示する。notification_level=mutedのIntentに関わる提案・成立はWeb Pushを送らず、アプリ内通知だけを作る(2026-10-21オーナー裁定・冒頭の決定記録(通知のAPI))。

**回答待ちと見送りの体験。** 自分がYESした後・相手の回答前は「相手の回答を待っています」と回答期限のみを表示し、それ以上の説明・催促はしない。回答取り消し(期限内)はこの状態から1操作で行える。見送りは1タップで完了し、当該提案は一覧から消える。見送り理由(任意)の入力は見送り完了後の独立した控えめな導線とし、未入力のまま閉じてよい(スキップを既定とする)。つながりIntentの見送りでは「この相手との提案は今後届きません」の説明を一度だけ表示し、機会Intentの見送りでは条件が変われば再提案され得る旨を同じ導線で示す。

**相手の離脱・終了の表示。** 相手の参加取り消し・ブロック・退会のいずれであっても、残された側には理由を開示せず「このつながりは終了しました」の中立な一文と読み取り専用の履歴のみを表示する(原因の区別を画面に出さない)。参加取り消し(leave)は成立後のLATCHから抜ける離脱の操作(1対1はチャットを双方読み取り専用にする)、LATCHの削除(DELETE)は自分の表示から消す操作である。続いている(matched)LATCHの削除は離脱を伴い、終了後(completed・成立後の取り消し)のLATCHの削除は相手の側の表示を変えない(2026-10-21オーナー裁定・冒頭の決定記録)。一覧の操作ラベルにその違いを反映する(説明文の分け方と確認の段は冒頭の決定記録(2026-10-21・チャットの画面))。

**Intentの期限切れ。** 期限切れ時はアプリ内通知(1回)で「預けていた意思の期限が切れました」を伝え、一覧の期限切れカードから同じ内容で再び預け直す導線を置く。期限切れを沈黙させない。

**状態の表示名。** 画面に表示する状態名は次の対照に従う(最終文言は`prototype/`のデザインシステム(文言集ボード)基準とする)。draft=下書き / active=預けている / paused=一時停止中 / expired=期限切れ / cancelled=取り下げ / proposed=回答を待っています / partial_accept=相手の回答待ち / matched=つながった / completed=終了。

**空状態。** Intent0件・提案0件の待機中画面は「待つことが正常な状態」を前提としたコピーとし、「候補が見つかりません」等の失敗を示す表現は使わない。

**一致度の非表示(2026-10-17オーナー裁定)。** 提案画面に一致度(LATCH Score)は表示しない。順序付けと計測のみに内部利用する(API応答のscoreはUIで描画しない)。

**提案画面の表示範囲(2026-10-19オーナー裁定)。** 提案画面には「どの意思への提案か」を表示しない(提案画面が示すのは提案の旨・回答期限・必要人数の3項目まで)。どの意思への提案かは、ホームの一覧で該当する意思のカードに状態表示名(proposed=回答を待っています)が付くことで示す。

## 第IV部 マッチングシステム

### 11. 基本方針 — 総当たりをやめ、イベント駆動で計算量を抑える

全Intent同士の総当たり比較は行わない。イベント駆動+候補検索+段階的評価の構造、作成・更新EventはEmbedding要求までを第1段、Embedding完了(embedding_completed)がLayer 1〜5の第2段トリガーとなる2段構成、削除・期限切れの即時処理、起点Intentから既存Intentインデックスへ候補を引きに行く比較の向き、debounce(更新10秒窓)・idempotency・version番号による重複防止、を適用する。

各層の出力上限Kは K_v=50 / K_c=20 / K_j=8(回数ベース) / グループPool=15 とする(運用データで調整する初期値)。

つながりIntentの再評価は、新規・更新Intentを起点とする候補検索で完結する。新規Intent Bの登録は、既存プールからAを引いて評価するため、A側に独自の再評価トリガーを要しない。**時間BucketとBucket到来Eventは機会Intentのみに適用する。** つながりIntentは、状態が変わらない限りスコアも変わらないため、定期的な再評価を行わない(Embeddingモデル更新時の一括再エンベディングと再評価は例外とする)。

### 12. 候補は5層で絞る

5層構造を両形式に適用する。各層の担当は次のとおり(層番号は絞り込みの概念順であり、実際の実行順(候補検索→硬絞り)は06が定める)。

**Layer 1 Hard Filter。** SQL・Index・Rule Engineで、ブロック・年齢(飲酒)・自己ペア・**同一ペア提案履歴**を判定する。機会Intentは時間・距離・予算・人数・カテゴリも判定する。つながりIntentは時刻を持たないため時間の厳密判定はなく、地理は両者が地域を添付した場合のみ重なりを判定する(非添付=全国)。出力はpass / failのみ。

**Layer 2 Candidate Retrieval。** 両形式共通の主役である。IntentをEmbeddingしてANN検索で意味的に近いIntentを引く。「個人開発をやっている人と繋がりたい」と「Railsで何か作っている。技術の話ができる相手が欲しい」を候補として近づけるのがこの層の役割だ。Embedding入力は、topicとsoft_constraintsを含む正規化テキストとする。

**Layer 3 Cheap Judge。** Jevに渡す前に、明らかに成立しにくい候補を低コストで除外する。

**Layer 4 Jev。** 原子的な問いに分解して成立可能性を判定する(第13節)。

**Layer 5 LATCH Engine。** Jevの結果・Hard Constraint・過去データを統合し、最終的な成立可能性(LATCH Score)を算出する。

**異形式間のマッチングは行わない。** つながりIntent×機会Intentのペアは候補化しない。formが同じIntent同士のみを候補とする。理由は2つある。第一に、両者は意味が違う(関係の要求と機会の要求)。第二に、意味の違うものをJevに判定させると精度と説明性が落ちる。ユーザーは「すぐ会う」意思と「関係を作る」意思を、formの確認で明示的に区別して預けている。この境界は、精度データの蓄積後に再評価する(将来的には「飲み仲間が欲しい」×「今夜飲める」の相互補完があり得る)。

### 13. Jev利用方針 — 単一スコアを出させず、原子的判断に分解する

Jevの判定規定は次のとおりである。原子的な問い(would_a_accept_b / would_b_accept_a / purpose_fit / mood_fit / timing_fit / social_fit / latent_yes)に分解し、1リクエストで並列評価させる。基本スコアは弱い側を基準に取る。

```text
MutualScore = min(P(A accepts B), P(B accepts A))
L = H × MutualScore × C
```

H: Hard Constraint(成立なら1、不成立なら0)、C: Calibration係数(初期値1)。閾値0.60(初期値)とする。Jevの入力は構造化データからの正規化テキストに限り、raw_textは送信経路に入れない。判定結果は数値のみを保存し、自由文(reason)は生成しない。System Oneモデル第一候補+生成LLMフォールバックの構成とする(プロバイダ契約は後続のLLM利用仕様書で確定)。

timing_fitは両形式に「時機の一致」として適用する。機会Intentでは日時の一致、つながりIntentでは「今すぐ集中的に始めたい」「ゆっくりでいい」という関係の温度・開始時期の一致を問う。軸の追加(接続継続性を問う軸等)は、運用データを見てからLLM利用仕様書で判断する。

### 14. 人間の行動を正解データにするCalibration

Jevの予測が当たっていたかは、提案への回答とその後の行動で検証する(構造を両形式に拡張)。

機会Intentの正解データは次のとおりである(実際に成立したか/実際に参加したか/キャンセルしたか。completed遷移時の1問自己申告)。

つながりIntentの正解データは、**チャット行動**から取る。観測点は次のとおりと確定する。

```text
チャット開始: 成立後7日以内に双方が1件以上送信したか
往復の継続:   成立後7日・30日のメッセージ往復数
負例:         ブロック・通報・無開始(7日間双方とも送信なし)
自己申告:     成立後7日時点の1問(「このつながりはどうでしたか」・スキップ可)
```

保存した結果をつなげると、Human Intent → Prediction → Proposal → Actual YES / NO → Actual Action という流れができる。Actual Actionの定義が形式ごとに異なる(機会=実際に会えたか、つながり=チャットが始まったか・続いたか)だけで、この連鎖の構造は変わらない。予測値と実際の人間行動との差をこのデータで継続的にCalibrationする方針、calibration_recordsテーブルによる形式化、削除・退会時の匿名化統計への丸め込みも適用する。

### 15. グループLATCH

最大4人、候補Pool=15、全員YES必要(部分成立なし)、集約スコア=全ペアMutualScoreの最小値、通知は集約スコア降順で1集合ずつ——とする。

つながりIntentでも人数の添付によりグループを表現できる。「3人集まるなら読書会を始めたい」は、つながりIntent×participants(min=3)であり、3人のつながり集合の成立として扱う。地域・時間帯・カテゴリによるPoolの限定条件は、つながりIntentでは「地域(添付時)・主題の近接」に読み替える。

グループ提案の提案履歴はペア単位で記録する。defer / noで閉じたときは閉じた本人を含むペアだけを、回答期限切れで閉じたときは有効なyesを持たない参加者を含むペアだけを記録し、それ以外のペアは履歴を消費しない。成立後の参加取り消し(leave)は本人だけを外して続け、残りが必要人数の下限を割ったときにLATCH全体をcancelledとする(2026-10-20オーナー裁定・冒頭の決定記録)。

### 16. イベント駆動処理(Queue・重複防止・補償)

Match Eventのキュー経由の非同期処理、debounce、idempotency key、version number、失敗時の再試行上限と隔離、外部LLM呼び出し失敗時に判定を保留して提案しない方針(誤った提案より提示の見送りを優先)を適用する。

期限前catch-upスキャン(expires_atまで2時間以内かつ直近評価から30分以上経過のIntentを60秒周期で回収)は**機会Intentのみ**に適用する。つながりIntentは期限切れバッチでexpiredへ遷移させる。Jevの実行予算(1Intentあたり1日40回・1ユーザーあたり1日120回)と同一Intent再評価の30分頻度制限(意味フィールドの更新は除く。2026-10-20オーナー裁定・冒頭の決定記録)、1評価世代内でのJev結果再利用(jev_result)も適用する。

### 17. データモデル

データモデルは5 Entity(User / Intent / MatchCandidate / Latch / MatchEvent)を基本とし、本書の要件に合わせて次のとおり定める。

```yaml
User:
  actor_type: individual      # v1.0は個人のみ。将来の供給側参加(店・施設)は
                              # actor_type=business として同じIntentモデルに乗せ、
                              # 既存テーブルの破壊的変更なしに拡張する(設計拡張点)
  # display_name / profile / birth_date / trust_score(予約)。性別は持たない(第22節)

Intent:
  form:            connection / occasion
  topic:           必須(主題の短句)
  category:        任意(低粒度タグ)
  time:            機会Intentは必須・つながりIntentはnull
  geo:             任意添付(つながりIntentでは活動地域)
  budget / participant_count / embedding / constraints系 / visibility /
  notification_level / status / version / starts_at / expires_at / …

MatchCandidate:    # intent_a_id / intent_b_id(+各form) / 各層スコア / jev_result / latch_score / status
Latch:             # intent_ids / user_ids / proposal / score / responses /
                   # status / response_deadline / expires_at / completed_at
MatchEvent:        # (event_typeに内部由来+embedding_completed)
```

加えて、**同一ペアへの再提案排除**のための提案履歴(ユーザーペア単位・提案の結果outcome付き)を保持する。恒久排除の判定はoutcomeがmatched(成立)またはrejected(明示拒否)の行の存在で行い、deferred(見送り)・expired(期限切れ)の行は機会Intentの条件付き再提案(第8節)の参照に使う。成立・拒否・見送り・提示後の期限切れの履歴は保持し、進行中の提案のために確保した行は、その提案が未提示のまま、またはシステムの都合で閉じた場合に解放する(第8節)。履歴は退会時に本人を含む行を削除し、Intent削除時は保持する(第21節。削除で取り消された進行中の提案の分は解放する)。blocks・reports・notifications・messages・calibration_records・latch_status_events(Mutual Latch Rate集計)も保持する。

### 18. 検索とインデックス

機会Intentは(user_id / status / category / starts_at / expires_at / geo / budget / participant_count + Vector Index)。

つながりIntentは status / form / category / geo(添付時)のIndexとVector Indexを持つ。地理非添付のつながりIntentは全国スコープで候補検索の対象になる。Embeddingに用いたモデルの識別子と版の記録、モデル変更時の再エンベディング対象の特定も行う。

## 第V部 品質・プライバシー・安全

### 20. 非機能要件

**提供形態。** レスポンシブWebアプリ(モバイルファースト)をPWAとして提供する。ホーム画面追加(インストール)、Web Push通知(VAPID)、Service Workerによる最小限のオフライン表示(待機中・成立一覧の閲覧程度)を要件に含める。ネイティブアプリ(iOS/Android)は利用定着後の拡張とし、v1.0ではストア公開しない(着手基準は未決D-05)。

性能の目標は次のとおり(Intent保存 p95 0.5秒以下、Parser構造化プレビュー p95 3秒以下、Candidate Retrieval p95 1秒以下、初期LATCH判定 p95 10秒以下、通知は判定後5秒以内、全件総当たり禁止)。つながりIntentは初期LATCH判定の計測起点をactive化の保存コミットから通知送信記録までとする点で同一に扱う。

コスト保護は3層(源流レート制限 / Jev予算 / 実行回数上限)とする。Jev実行回数の上限は1日30,000回・1か月600,000回・80%到達でalert・上限時はJev未判定として保留とする。長寿命のつながりIntentが増加することに伴い、**Vector DBの容量とEmbeddingの保持コスト**を監視項目に加える。期限切れIntentのEmbedding遅延削除(期限+7日)を運用項目とする。

Observabilityの3群(パイプライン / Jev / 提案と行動)に、**つながり品質群(チャット開始率・往復数・ブロック率)**を加える(第23節)。アクセス系基本計測(DAU・再来訪)も行う。

### 21. プライバシー — 潜在意思を扱う以上、通常のSNSより厳しく

このサービスは「まだ誰にも言っていない意思」を扱う。次の規定を適用する。

- Intentは原則非公開とし、マッチング処理のみで利用する
- LATCH成立前に、相手へIntent全文を公開しない
- 成立前の条件サマリは一切開示しない(visibilityはhidden_until_matchの単値。summary_onlyはv1.0では存在しない・2026-10-17オーナー裁定)
- ブロック対象とは絶対にマッチさせない
- 退会時には、Intent本文・構造化データ・embedding(Vector DBを含む)・当該Intentを含むCandidate・提案履歴(本人を含むペアの行)を削除する。Intent削除時は、同一ペア再提案排除(第8節)のため成立・拒否・見送り・提示後の期限切れの提案履歴を保持する(削除で取り消された進行中の提案のために確保した行は解放する)
- 表示の最小化(相手に見せる情報は成立判断に必要な最小限)
- プッシュ通知の本文は汎用文とし、成立前の意思・条件サマリをOS通知経路に載せない
- ログ・計測・Analyticsにraw_text・正確な位置・NG条件を含めない(許可リスト方式)
- JevとEmbeddingへの送信は構造化データからの正規化テキストに限り、raw_textを送らない。Parserのみ、解析対象であるユーザー入力文(raw_text・最大300字)を送信する(同意文言は07 §8の系統別文言)。送信先と送信データの種別を記録する。プロバイダ契約には学習利用禁止等を含める
- 判定結果の保存に個人由来の自由文を含めない。match_candidates・group_candidatesは30日で定期削除
- 削除・退会時、Calibration用データはID系を除去した匿名統計として保持する

位置情報の丸め(地域名のみ表示・約1kmグリッド丸め・座標と距離の数値は非表示・セルフホスト地物データによる内部変換)は**地理を添付したIntentにのみ**適用する。地域を添付しないIntentは地名自体を表示しない。

### 22. 安全要件

3群の整理(相手からの防護 / 公開の制御 / プラットフォームの防護)を行い、Safety完了条件は5項目(ブロック・通報・Intent全文非公開・正確な現在地の非公開・飲酒Intentの年齢制限)とする。

安全上の設計判断は次の4つである。

**出会い系サイト規制法への非該当を維持する設計。** (i) 異性交際の機会の提供を事業目的としない。(ii) 性別を収集・判定・表示に使わない。**v1.0では性別の登録項目を持たない**と確定する。将来収集する場合もマッチング判定には使わない。(iii) 利用規約で交際・出会い目的の使用を禁止する。(iv) 将来の課金は、性別・交際目的と無関係な機能課金(通知枠・上限緩和等)のみとする。ジャンルを問わないサービスであるほどこの線を明示的に引く必要がある。

**営業・勧誘目的への構造的耐性。** Xの「#繋がりたい」文化は営業アカウントと混ざり合っている。本サービスは構造的に強い。相手を検索できず、成立前はプロフィールすら見えず、提案には相互YESが必須で、通知頻度に上限がある。営業目的のアカウントは「意思を置いて待つ」以外の道を持たない。ブロック・通報・レート制限(Active Intent 5件/ユーザー・作成20件/日・更新6回/時間の初期値)と組み合わせて、追加の自動検知は行わない(通報による手動対応)。

**年齢制限。** 利用登録は18歳以上(生年月日は自己申告)。飲酒を含む機会Intentは20歳未満のユーザーが作成できず、20歳以上同士の間でのみ候補になる。alcohol_involved判定の精度条件(recall 100%・precision下限90%)も適用する。つながりIntentは飲酒を条件に含められない(時間・場所を持たないため)。

**規制領域の禁止と法務確認。** 転職(職業安定法)・売買(古物営業法等)・交際目的の使用を利用規約で禁止する。**リリース前に弁護士等による法務確認を完了することを完了条件に含める**(第25節)。

アクセス制御(全API認証済みユーザーのみ、操作は所有者本人または提案の参加者のみ、開示範囲とブロックの判定はサーバ側で強制、Google+AppleのIdPトークン検証+独自JWT、成立後ブロックの即時適用とチャット読み取り専用化)をすべて適用する。成立後のブロックはブロックした本人の参加取り消しとして扱い、1対1はLATCH全体を終え、グループは本人だけが抜ける(2026-10-21オーナー裁定・冒頭の決定記録(安全のAPI))。

## 第VI部 完了条件

### 23. 成功指標

North Star Metricは Mutual Latch Rate とする。

```text
双方がYESした提案数 ÷ 当該期間に通知を送信した提案数
```

数え方の規定(分母=当該期間に通知を送信した提案数、1提案1計上、グループも1提案、期限切れ・no・cancelled(競合を含む)を分母から除かない、分子=必要人数全員がYESした提案数、ベースラインは公開後4週間中央値・前期比−5pt以内)とし、検証・評価文書(09)が詳細を確定する。

主要KPIは4群に分けて追う。

- 使われ方: Intent作成率 / Intent再作成率 / 1ユーザーあたりActive Intent数 / 7日・30日継続率
- マッチングの質: Candidate生成率 / 提案提示率 / 保留→expired率 / YES率 / Mutual Latch Rate / 無回答率
- **つながりの品質**: チャット開始率(成立後7日) / 往復継続率(30日) / ブロック率 / つながりあたりの成立LATCH数
- コスト: 1 IntentあたりJev実行数 / 1成立あたりAIコスト

形式別(つながり/機会)の内訳を必ず残す。前提6(分散密度)の確認材料は、つながりIntentの地域分布(添付・非添付)と提案・成立の地域交叉(同一地域内成立 vs 地域をまたぐ成立)である。

### 24. 品質評価

Offline評価は、ゴールドセットによる予測と実際のYES/NOの比較、構造化精度のフィールド別完全一致率(機会Intent: category 85% / time.start 90% / location 90% / participants 80% / budget 90%)で行う。加えて次の2つを行う。

- **form判定精度**: つながり/機会の完全一致率(合格基準: 90%以上)。formの取り違れは提案の意味そのものを壊すため、品質評価の対象とする
- **topic抽出精度**: 主題の短句の一致率(判定規則は後続文書で確定。未決D-03と同時)

alcohol_involvedの条件(recall 100%・precision下限90%)は適用する。C係数の再計算手順(四半期ごとのECE・Brier判定、変更はOffline通過とA/B適用を条件とする)も適用する。

Online評価はA/B Testで行う。対象は通知閾値・Candidate数(K_v)・通知文・回答期限(つながり24時間)・通知頻度・**form確認UIの文言**(form取り違えの抑止)とする(表示情報量のA/Bはvisibility単値化により行わない)。ユーザー単位の割付、混在ペアは対照値、判定不能時は既存基準維持の持続規定、ベースライン計測期間中の変更凍結——いずれも適用する。

**社内クローズドテスト(品質保証)。** 公開前に、全機能に対する内部クローズドテスト(E2E試験・実機確認)を実施する。これは検証のための段階リリースではなく、出荷前の品質保証である。実施条件を第25節の完了条件に含める。

## 第VII部 原則と核心

### 27. 設計原則

判断に迷ったとき戻る場所として、9つの原則を置く(基本8原則に、本コンセプトに直属する1原則を加える)。

1. AIに全件探索させない。検索・Index・DBで99%以上を削る
2. Hard Constraintはコードで判定する。AIに絶対条件を任せない
3. JevはJudgeとして使う。検索エンジンにはしない
4. 人ではなくIntentを評価する。恒久的な相性ではなく、目的と時点におけるつながりの成立可能性を扱う
5. 片方向の高評価をLATCHとしない。双方の成立を重視する
6. 実際の人間行動を正解データとする。YES / NO / チャットが続いたか / 実際に会ったかがGround Truth
7. 全件再計算ではなくEvent Driven。変化したものだけを再評価する
8. LATCH前はIntentを非公開。潜在意思を公開SNS化しない
9. **探す・見せる機能を持たない。** ユーザーは誰も検索できず、見つけることも見つけられることも、意思の一致を通してだけ起こる(画面コピーでも相手を「探す」語は使わない)

### 28. プロダクトの核心

このサービスは、人を検索するサービスではない。世界中に存在する「条件付きの意思」を待機状態にしておき、成立可能になった瞬間だけ接続するネットワークである。

技術的な核心は、Event Driven Matching、Candidate Retrieval、Semantic Judgment、Mutual Acceptance Prediction、Human Feedback Calibrationの5つの組み合わせである。時間と場所は意思の必須要素ではなく、任意に添付できる条件の一つである。

ユーザー体験としての核心はもっと短い。

> 探さなくていい。繋がりたいことを、置いておけばいい。

v1.0で完成させるのは、この体験そのものである。前提3(双方YESの予測精度)と前提6(地理的に分散しても成立する密度)を、リリース後の計測で確認し、壊れていれば直し、健やかならば広げる。
