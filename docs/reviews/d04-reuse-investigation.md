# D-04 記録 — 旧実装(latch-legacy)の扱いと技術スタックの新規選定

- 日付: 2026-10-17(v0.1→v0.2: 同日・決定変更)
- 対象: 旧リポジトリ latch-legacy / 新規リポジトリ latch
- 本書の位置づけ: 01 要件定義書の未決事項D-04(新規リポジトリの構成と旧実装の扱い)の確定記録

## 1. 決定の推移

- **v0.1(2026-10-17・初回)**: 新規リポジトリの構成(モノレポ: docs/backend/frontend/prototype)を確定し、旧実装からの再利用判定(開発基盤・認証・パイプライン骨格・LLM統合は移植、frontendは再構築、Cloudflare二重実装は保留)を定めた
- **v0.2(2026-10-17・プロダクトオーナー決定・現行)**: 上記の移植方針を撤回する。docs/以外のリポジトリ内ファイル(README・.gitignore)を削除し、**技術スタックを含めてすべて新規に選定してやり直す**

## 2. 現行の決定

1. 新規リポジトリ(latch)は **docs/ のみ** で運営を開始する。backend/frontend等のディレクトリと骨組みは、技術選定の後に作る
2. **旧実装(latch-legacy)からのコード・技術スタックの移植は行わない。** 技術スタック(言語・フレームワーク・DB・メッセージング・配備先)は04(アーキテクチャ設計書)でゼロベースから選定する。旧スタック(Python/FastAPI・PostgreSQL・Redis・Cloudflare Workers)も比較のうえで再選され得るが、既定とはしない
3. 旧リポジトリは**参照専用のアーカイブ**とする。許される利用は「読んで知見を得ること」に限る(コピー・移植はしない)
4. 旧実装で証明された設計知見(5層パイプラインの段階的絞り込み・コスト保護・プライバシー/安全設計・開発規律)は、**コードではなく要件・設計文書(01・02・04以降)経由で引き継ぐ**

## 3. 旧実装の資産一覧(在庫記録・参照用)

移植は行わないが、04の技術選定と実装時に参照する知見の所在を記す。

| 領域 | 旧実装の内容 | 参照価値 |
|---|---|---|
| 開発基盤 | compose常設環境・Makefile・mise/uv・ruff・pytest規律・CI | 開発規律の設計(毎コミットlint/test・Clock抽象・ログ許可リスト) |
| 認証 | IdPトークン検証+JWT発行・回転式リフレッシュ・Redis失効リスト | 認証要件(01 §22)の実現方式の実例 |
| パイプライン | 5層・Event Queue・debounce・idempotency・K上限・Jev予算・circuit breaker | 01 §11〜§16の元になった実装詳細 |
| DBスキーマ | alembicマイグレーション・PostGIS・geofeatures | フィールド設計・位置丸めの実現例 |
| LLM統合 | Parser/Embedding/Jev・stub/real両モード・精度ゲート資産 | プロンプト・スキーマ・評価の実例 |
| frontend | Vite+React・vitest・Playwright E2E・録画ギャラリー | テスト基盤の設計 |
| Cloudflare | Workers+D1+Queues・契約試験 | 配備先候補の1つとしての実測データ |
| テスト・文書群 | unit/contract/E2E・docs 00〜13・plans・reviews | 旧文書群=01・02の「踏襲」の引用元 |

## 4. 04(アーキテクチャ設計書)への引継ぎ事項

技術選定は次の論点からゼロベースで行う。

- 配備形態(単一ホスト・PaaS・サーバーレス等)と配備先
- 言語・フレームワーク(バックエンド・フロントエンド)
- データベース(リレーショナルとベクトル検索を一体にするか分離するか)
- メッセージング/キューとイベント駆動の実装
- 認証(IdP検証・セッション)の実装
- Web Push(VAPID)・PWAの配信方法
- 開発環境・CI・テスト戦略(02 §4の#1〜#35をどう自動証明するか)
- コスト保護(LLM予算・レート制限)の実装
