### 1.1 試験の前の準備(Step 0)

stagingには手動の試験で使った利用者が2人いて、それぞれ有効な意思を持っていた。負荷試験の提案がこの2人に届かないよう、オーナーの決定により、2人の有効な意思を削除API(`DELETE /v1/intents/{id}`・ベクトルも消える)で取り下げた。オーナーの依頼により代行して実行した。

- 1人目: 有効な意思1件 → 1件削除
- 2人目: 有効な意思1件 → 1件削除
- 削除の後、`load-`以外の利用者の有効(active/paused)な意思が0件であることを、読み取りの問い合わせで確かめた

## 2. 実行の手順

手順書`docs/runbooks/staging.md` §7のとおりに実行した。各シナリオの前に、stagingのD1で`SELECT count(*) FROM match_events WHERE status='pending'`が0であることを確かめた。提案を待つ上限は、反映の後の評価し直しに掛かる時間を見込んで`-e PROPOSAL_WAIT_SEC=300`とした。

```bash
export LATCH_LOAD_BASE_URL=<stagingのURL>
RUN_ID=202610221144
node tools/load/cleanup.mjs
node tools/load/run.mjs tools/load/scenarios/a-intent-burst.js -e RUN_ID=$RUN_ID --summary-export tools/load/results/$RUN_ID-a.json

node tools/load/cleanup.mjs
node tools/load/run.mjs tools/load/scenarios/bd-proposal.js -e MODE=burst -e RUN_ID=$RUN_ID -e PROPOSAL_WAIT_SEC=300 --summary-export tools/load/results/$RUN_ID-d.json
```

(a)の後の後始末だけは、意思の削除が非常に遅くなったため手順どおりには終わらなかった(§6のissue #16)。`cleanup.mjs`と同じAPIの手順を10人分並べて行う一時的なスクリプト(git管理外)で、残りを消した。(d)と(c)は、準備の途中で手元の回線の接続が切れて(`connection reset by peer`)止まったため、同じ実行の印でもう1回実行した。準備で登録済みの利用者は、2回目にはそのままサインインし直して使われる。

### 4.3 初期判定が目標を外れた理由

組の2人はほぼ同時に意思を保存する。先に評価した側からは、相手のベクトルがまだVectorizeに反映されておらず見えない。提案は、自分のベクトルの反映を確かめた後の評価し直し(06 §2)で作られる。そのため初期判定の値は、ほぼVectorizeの反映の時間になる((d)は最小69.88秒・p50 251.96秒・最大272.96秒)。これは不具合の修正工程の設計で見込んでいた結果である。先に反映済みの相手がいる意思なら、すぐに見つかって提案される。

(d)では第1段の待ちも長かった。embedding_completedの行の作成は、保存から2.3〜73.7秒後(p50 50.8秒)だった。不具合の修正工程の確認(1件ずつ)では11〜16秒だった。

意思は1つにつき2回評価される(すぐの評価と反映の後の評価し直し)。そのぶん、Layer 2 Candidate RetrievalとD1への書き込みはおよそ2倍になる。Jevの結果は保存したものを使い回す。

### 4.4 通知が目標を外れた理由(推定)

キュー経由で作った提案のWeb Pushは、主キューのバッチの処理がすべて終わった後に送る。バッチの初めのほうで作った通知は、同じバッチの残りの評価が終わるまで待つ。(d)の間に`wrangler tail`で見たバッチの所要時間は、最大23.1秒だった。不具合の修正工程の確認では、キュー経由の最初の提案のpushは通知の行の作成から7.6〜13.0秒後だった。今回の(b)は7.51〜30.08秒(p50 17.05秒)、(d)は3.25〜6.44秒(p50 4.23秒)だった。
